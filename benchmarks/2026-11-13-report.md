# Benchmark report — 2026-11-13

Ticket **T34**. Every number here was measured on the machine described below. Nothing is
estimated, extrapolated or borrowed from another system.

**The load generator shares a laptop with everything it is testing.** That is the most important
line in this report. These numbers are good for comparing *this system against itself* before and
after a change, and they are not a capacity estimate for anything. A staging environment with the
database on its own instance will produce different absolute figures, and `docs/SECURITY_AND_TESTING.md`
§6's "p95 under 500 ms" stretch objective should be judged there, not here.

## Reproducing it

```bash
createdb opspilot_bench && psql -d opspilot_bench -c 'CREATE EXTENSION vector'
make bench                      # baseline
BENCH_LABEL=after make bench    # label a second run
```

`make bench` loads the fixture, starts its own API with a throwaway test-issuer key, mints its own
token, runs k6 and writes the raw summary to `benchmarks/results/`. It needs no Redis, no worker
and no Docker. The fixture is reloaded on every run — it deletes and recreates its two tenants —
which matters because **the load test itself inserts tickets**: the `create` scenario added ~25,000
rows during the baseline run, and comparing a second run against that polluted table would measure
the pollution.

Load profile: 30 VUs for 60s, then 100 VUs for 20s. §6 specifies 30 VUs for ten minutes then a
burst of 100; the shape is kept and the duration cut, because ten minutes of saturation on a
laptop measures thermal throttling as much as the application.

## The change

Two changes, both to the ticket list, both measured before shipping.

### 1. An index matching the actual ORDER BY (`V007__ticket_list_index.sql`)

The list query orders by `(created_at DESC, id DESC)`. The only index was
`(organization_id, status, created_at DESC)` from V002 — `status` in the middle, no `id`. Excellent
for a filtered list, useless for ordering an unfiltered one.

**Before** — the default page the UI loads:

```
Limit (actual time=2.216..2.222 rows=21)
  Buffers: shared hit=642
  ->  Sort (Sort Key: created_at DESC, id DESC; top-N heapsort)
        ->  Seq Scan on tickets (rows=10000, Rows Removed by Filter: 1003)
Execution Time: 2.253 ms
```

**After**:

```
Limit (actual time=0.328..0.337 rows=21)
  Buffers: shared hit=17 read=3
  ->  Index Scan using idx_tickets_org_created_id
Execution Time: 0.354 ms
```

**6.4× faster, 32× fewer buffers.** The old index is kept: the *filtered* page still plans as an
Index Scan on it at 0.061 ms, and dropping it would regress that path.

### 2. A row-value cursor predicate (`TicketRepository.findPageAfterNative`)

With the index in place the deep page still behaved badly, and the plan said why:

```
OR form      Index Scan + Filter, Rows Removed by Filter: 5001
             Buffers: shared hit=30250,  Execution Time: 4.109 ms
```

PostgreSQL cannot push `a < ? OR (a = ? AND b < ?)` into an index condition, so it walked the index
from the newest row and discarded everything before the cursor. **The cost grew with page depth —
the precise failure keyset pagination exists to prevent**, hidden behind an index that looked like
it was being used.

A row-value comparison is a single operation the index understands:

```
(created_at, id) < (?, ?)

row form     Index Scan, predicate inside Index Cond, no rows removed
             Buffers: shared hit=6,  Execution Time: 0.038 ms
```

**108× faster, 5,000× fewer buffers.** Both plans use the same index; the difference is entirely
*where the predicate runs*.

JPQL has no row-value syntax, so this one query is native SQL. That is the whole justification for
the exception, and it is recorded in the method's javadoc next to the measurement.

### Why `create` and `run status` also got faster — and why that is not a claim

Neither endpoint touches either changed query. They improved by roughly two thirds anyway.

The honest reading is **contention, not optimisation**. Everything here shares one laptop: one
PostgreSQL, one JVM, one CPU. The list endpoint was sequentially scanning 11,003 rows on every
request at over a thousand requests per second; removing that freed buffer cache, CPU and database
connections for everything else. The other endpoints did not get faster — they *stopped waiting*.

This is inference from the setup, not something the benchmark measured directly. On an environment
where the database has its own instance the effect would be much smaller. It is written down
because the alternative — reporting "ticket creation is 65% faster" — would be a fabricated claim
about a code path that did not change.

## What this does not measure

- **Model latency.** No endpoint under test calls a provider. The run-status scenario deliberately
  reads a run left `QUEUED` with no worker running, so the figure is the API's read path and
  nothing else. §6: "Do not confuse LLM run latency with synchronous HTTP latency."
- **Network.** Loopback only. No TLS, no load balancer, no internet round trip. Real p95 from a
  browser will be dominated by things absent here.
- **Concurrency against a shared database.** One API process. Nothing here says how the system
  behaves with several instances contending for the same pool.
- **Knowledge retrieval.** §6 also specifies 1,000 and 200 knowledge chunks per tenant; the fixture
  creates tickets only. Vector search is unbenchmarked, and on a 1,536-dimension column it is the
  most likely next bottleneck.
- **Sustained load.** 60 seconds, not ten minutes. Nothing here would catch a slow leak.

## Remaining bottlenecks and limits

1. **`AgentRunRepository.findPageAfter` has the identical OR-shape** and will degrade the same way
   once a tenant has many runs. The fix is known and measured; it is not applied because it has not
   been benchmarked, and the rule here is that an optimisation ships with its own evidence.
2. **Vector search is unmeasured.** The likeliest next bottleneck, and there is no HNSW index —
   `docs/SECURITY_AND_TESTING.md` §1 raises comparing exact and approximate recall if one is added.
3. **No connection-pool sizing work.** The pool is at its defaults, now with the 2-second
   connection timeout T33's drill added. At 100 VUs the pool is the obvious next limit and was not
   investigated.
4. **The `create` path inserts a customer per call.** Realistic for a first contact, pessimistic for
   steady state, so its figure is a lower bound on a cheaper mix.
5. **Absolute numbers are laptop numbers.** Worth repeating once more: use these to compare this
   system against itself, and re-measure on staging before claiming anything about capacity.
