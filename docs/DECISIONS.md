# Architecture Decision Record

## ADR-001 — Modular Java backend plus separate Python AI worker

Status: **Accepted as blueprint decision**. Reason: demonstrate business service engineering and specialized AI orchestration without creating artificial microservices. Tradeoff: inter-service contracts and dual-language testing.

## ADR-002 — Postgres as source of truth, Redis Streams as event transport

Status: **Accepted as blueprint decision**. Every critical business write and outbox insertion is transactional in Postgres; workers are idempotent. Tradeoff: outbox/lease logic requires deliberate testing; exactly-once delivery itself is not claimed.

## ADR-003 — Approval is enforced by deterministic server policy

Status: **Accepted as blueprint decision**. Agent text and tool proposals are untrusted. Only specific server-authorized actions run; publishing a reply requires approved immutable proposal. Tradeoff: less autonomous but safer and easier to reason about.

## ADR-004 — Auth0 for production identity; offline signed fixture for tests

Status: **Accepted as blueprint decision**. Avoid reinventing password/session security. Tradeoff: manual identity-provider setup; tests need isolated signed fixtures that never run in production.

## ADR-005 — Exact tenant-scoped vector search first

Status: **Accepted as blueprint decision**. Small datasets benefit from simpler correctness baseline. HNSW is a future measured optimization, given tenant filtering can affect approximate recall.

## ADR-006 — No LICENSE file committed in T00

Status: **Accepted, pending owner decision**. `AGENTS.md`/T00 only calls for a LICENSE "placeholder only if rights are clear." The repository owner has not yet chosen a license (e.g. MIT vs. all-rights-reserved for a private portfolio repo), so none is added in T00 to avoid asserting terms the owner has not approved. Add a real `LICENSE` file in a later ticket once the owner picks one; until then the repository defaults to all-rights-reserved.

## ADR-007 — No Postgres bootstrap/init SQL in T01; Flyway alone owns `CREATE EXTENSION vector`

Status: **Accepted**, 2026-11-05. `docs/TASKS.md` T01 says to "create bootstrap SQL only for extensions if required." The `pgvector/pgvector:pg16` image ships the extension's shared library already available to any database on that instance, and `CREATE EXTENSION vector` does not need `shared_preload_libraries` or a superuser-only init step beyond what a normal migration role can run. So `infra/docker-compose.yml` mounts no `docker-entrypoint-initdb.d` scripts; the extension is created exactly once, by the Flyway `V001__extensions_and_core.sql` migration in T06, matching `docs/DATA_MODEL.md`'s migration sequence and avoiding two different places that could both try to create the same extension. Tradeoff: a developer who only runs `make infra-up` without ever starting `services/api` (and therefore never running Flyway) will see pgvector reported as "not created yet" by `scripts/check-infra.sh` — this is expected and documented in the script's own output, not a bug.

## ADR-008 — Spring Boot 4.1.2, and its restructured autoconfiguration packages

Status: **Accepted**, 2026-11-05. `docs/DEPENDENCY_DECISIONS.md`'s baseline target was "Spring Boot stable compatible with Java 21" without a pinned version; verifying against Spring Initializr's live metadata (AGENTS.md rule 4) at T02 time found Spring Boot 4.1.2 as the current stable GA release (4.2.0 is still milestone/RC only). This is a major-version jump past what either the blueprint author or this assistant had prior knowledge of, and it moved many autoconfiguration classes out of `org.springframework.boot.autoconfigure.*` into per-module packages, e.g.:

- `org.springframework.boot.autoconfigure.orm.jpa.HibernateJpaAutoConfiguration` → `org.springframework.boot.hibernate.autoconfigure.HibernateJpaAutoConfiguration`
- `org.springframework.boot.autoconfigure.flyway.FlywayAutoConfiguration` → `org.springframework.boot.flyway.autoconfigure.FlywayAutoConfiguration`
- `org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration` → `org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration`
- `org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest`/`AutoConfigureMockMvc` → `org.springframework.boot.webmvc.test.autoconfigure.*`
- `org.springframework.boot.test.web.client.TestRestTemplate` → `org.springframework.boot.resttestclient.TestRestTemplate` (and needs an explicit `@AutoConfigureTestRestTemplate`, plus a `spring-boot-restclient` dependency this project doesn't currently have — see `docs/DEPENDENCY_DECISIONS.md` T02 notes; T02's one security integration test uses MockMvc instead, which needed no extra dependency).

**Action for future tickets:** do not copy Spring Boot 2.x/3.x class names, annotation package paths, or Stack Overflow snippets from memory — verify the actual class in the resolved `~/.m2` jar (or current official docs) before using it, exactly as AGENTS.md rule 4 already requires for dependency *versions*. This caught real compile/runtime errors during T02 and will keep doing so for T06+.

## ADR-009 — Next.js 16 Cache Components, and verifying against its own bundled docs

Status: **Accepted**, 2026-11-05. `create-next-app@16.4.5` (the current stable, verified against npm's registry, not assumed from memory) scaffolds new apps with `cacheComponents: true` and `partialPrefetching: true` by default — a materially different rendering model (Partial Prerendering, `"use cache"`, the `instant` route segment config) from pre-16 Next.js. `next dev` itself auto-generates `apps/web/AGENTS.md` on every run, explicitly warning that "this version has breaking changes" and pointing at `node_modules/next/dist/docs/` as the authoritative reference — not a training-data assumption. That generated file is committed on purpose (it's idempotent and harmless) rather than fought.

**Action for future tickets (T08–T12, T22, T27):** before writing data-fetching, auth-cookie, or polling code in `apps/web`, read the relevant guide under `node_modules/next/dist/docs/01-app/`, the same way ADR-008 requires verifying Spring Boot 4 classes against the actual resolved jars.

## ADR-011 — CI: GitHub Actions pinned by commit SHA; Dependabot over Renovate; gitleaks as a personal-account repo

Status: **Accepted**, 2026-11-05. Every third-party action in `.github/workflows/ci.yml` is pinned to an exact commit SHA (with the human-readable version as a trailing comment), not a floating tag — `astral-sh/setup-uv`'s own README recommends this, and it matches `docs/SECURITY_AND_TESTING.md`'s supply-chain mitigation ("protected main branch" etc.): a tag can be force-moved to point at different code; a commit SHA cannot. SHAs were resolved from each action's own tag refs (`git ls-remote`), not guessed.

Dependabot (native, config-file-only) was chosen over Renovate because Renovate requires installing a separate GitHub App and authorizing it on the repository — a human/account action outside what a config file alone can set up — while Dependabot needs nothing beyond `.github/dependabot.yml`. `package-ecosystem: uv` is used for `services/agent` (confirmed as a distinct, supported ecosystem from `pip`, not a guess).

`gitleaks/gitleaks-action@v3` requires a paid license (`GITLEAKS_LICENSE` secret) only for repositories owned by a GitHub **organization**; personal-account repos (this one, under `abram0102`) need no license. If this repository is ever transferred to an organization, add that secret or switch to running the open-source `gitleaks` CLI directly.

## ADR-013 — Plain UUID foreign-key columns in JPA entities, not `@ManyToOne`; composite FKs enforce tenant isolation at the DB level

Status: **Accepted**, 2026-11-05. T06's entities (`Ticket.customerId`, `TicketMessage.ticketId`, `Membership.organizationId`/`userId`, etc.) store foreign keys as plain `UUID` fields rather than Hibernate-managed `@ManyToOne` associations. This keeps every tenant-scoped query explicit (`findByIdAndOrganizationId(...)`, never a bare `findById`) and avoids lazy-loading/N+1 surprises across what will become a large entity graph. It also sidesteps a genuine Hibernate mapping difficulty: the DB's composite foreign keys (e.g. `tickets.(customer_id, organization_id)` → `customers.(id, organization_id)`, added specifically so the database itself rejects a ticket referencing another organization's customer — docs/DATA_MODEL.md section B.2's literal example) don't map cleanly onto a `@ManyToOne` when one of the two FK columns (`organization_id`) is already its own mapped field on the owning entity.

Verified with real tests, not just asserted: `TicketRepositoryIntegrationTest.ticketCannotReferenceACustomerFromAnotherOrganization` inserts a cross-tenant ticket and asserts the DB itself (`DataIntegrityViolationException`), not application code, rejects it.

## ADR-015 — Testcontainers' Postgres image must be `pgvector/pgvector:pg16`, not plain `postgres:latest`

Status: **Accepted**, 2026-11-05. T02's Spring Initializr scaffold generated `TestcontainersConfiguration` pointing at plain `postgres:latest`. That went unnoticed through T02–T05 because no Flyway migration existed yet for it to matter. T06's first real CI run (confirmed via the actual GitHub Actions log, not guessed — see below) failed all Docker-backed tests with `ERROR: extension "vector" is not available`: `V001__extensions_and_core.sql`'s `CREATE EXTENSION vector` has no shared library to load against stock Postgres. The root cause was then found by grep, not guesswork. Record this path for future CI failures in this environment: ask the operator for the downloaded log archive rather than assuming log/API access.

## ADR-016 — Jackson 3 (`tools.jackson.*`), not `com.fasterxml.jackson.*`, in this Spring Boot 4 stack

Status: **Accepted**, 2026-11-05. Needed `ObjectMapper` for T07's JSON-writing security error handlers and found `com.fasterxml.jackson.databind` simply isn't on this project's classpath — Spring Boot 4.1.2 pulls in `spring-boot-starter-jackson` → `tools.jackson.core:jackson-databind:3.1.7`, Jackson's real "Jackson 3" release, which moved `databind`/`core` to a new Maven groupId (`tools.jackson.core`) **and** a new package namespace (`tools.jackson.databind.ObjectMapper`, `tools.jackson.core.JacksonException`, etc.) — `jackson-annotations` alone stays at the old `com.fasterxml.jackson.core` coordinates. `JacksonException` is now an unchecked `RuntimeException` (previously checked `IOException`-derived). Verified by inspecting the resolved jar's actual class list rather than assuming Jackson 2's API, the same discipline ADR-008 established for Spring Boot 4's autoconfiguration packages.

**Action for future tickets:** anything using Jackson directly (custom serializers, `@JsonProperty` on non-entity DTOs, etc.) must import from `tools.jackson.*`, not `com.fasterxml.jackson.databind`/`com.fasterxml.jackson.core`.

## ADR-017 — T07 security architecture: lazy real decoder + conditional test-issuer decoder, composite with test-first fallback

Status: **Accepted**, 2026-11-05. Implements docs/TASKS.md T07's "signed-token test infrastructure" as two independently-built `JwtDecoder`s rather than one:

- The **real** decoder (`JwtDecoderConfig.issuerJwtDecoder`), built from `app.security.oidc-issuer-uri` via `JwtDecoders.fromIssuerLocation(...)`, marked `@Lazy` so its (otherwise eager) OIDC-discovery HTTP call never runs at application startup — critical because `API_OIDC_ISSUER_URI` is a placeholder until T08, and eager resolution would break every environment without live Auth0 configured, local dev and CI included. Deliberately **not** using Spring Boot's own auto-configured resource-server `JwtDecoder` (triggered by the standard `spring.security.oauth2.resourceserver.jwt.issuer-uri` property) for the same reason — that auto-configuration is not lazy. This project's own `app.security.*` properties are used instead, specifically to keep decoder construction lazy.
- The **test-only** decoder, built only when `app.security.allow-test-issuer=true` (default `true` under the `local` profile, hard-refused under `production` by `ProductionSafetyGuard` — the literal T07 acceptance check "production profile refuses test-only issuer"), validated against an RSA key pair this same process generates fresh at startup (`TestIssuerConfig`) — no key material of any kind lives in source control.

The two are combined by `TestFirstDelegatingJwtDecoder`: try the test decoder first, fall back to the real one only on failure. This is deliberately **not** routed by peeking the token's own unverified `iss` claim — that would let a test-signed token which fraudulently claims some other issuer skip the test decoder entirely, masking the actually meaningful rejection (wrong issuer/audience/expired) behind the real decoder's unrelated "can't reach placeholder issuer" failure. Trying the test decoder first means its signature check runs regardless of claimed issuer, so every rejection test (`JwtAuthenticationIntegrationTest`) gets the semantically correct failure reason.

**Consequence discovered while implementing, not predicted up front:** wiring `UserRepository` into `SecurityConfig` (so `PrincipalResolvingJwtAuthenticationConverter` can resolve the caller) means the security filter chain itself now depends on a real datasource — so even "no bearer token -> 401"-style tests can no longer exclude DataSource/JPA/Flyway autoconfiguration the way T02's original `SecurityConfigIntegrationTest` did. That test was updated (now Testcontainers-backed, and its "every other path" assertions changed from `isForbidden()` to `isUnauthorized()` since `anyRequest().authenticated()` replaced `anyRequest().denyAll()`) rather than left broken or deleted.

## ADR-018 — `@Lazy` on a `@Bean` method does nothing unless the injection point also defers resolution

Status: **Accepted**, 2026-11-06. T07's first real CI run (confirmed via a manually downloaded log archive, same pattern as ADR-015) failed every Docker-backed security test: `UnsatisfiedDependencyException` building `jwtDecoder`, caused by `issuerJwtDecoder` throwing `Unable to resolve the Configuration with the provided Issuer of "https://REPLACE-ME.auth0.com/"` — the exact eager OIDC-discovery call ADR-017's `@Lazy` annotation was supposed to prevent.

**Root cause:** `@Lazy` on a `@Bean` method only defers that bean's construction *until something asks for it* — it does not make an injection point itself lazy. `jwtDecoder(JwtDecoder issuerJwtDecoder, ...)` declared `issuerJwtDecoder` as a plain method parameter, so Spring had to fully resolve it (triggering the real decoder's construction and its live network call) just to build `jwtDecoder` itself, regardless of `@Lazy` on the producing bean. This only surfaces when something actually depends on the lazy bean directly — which is exactly why it passed local compilation and Docker-independent tests and only broke under the Docker-backed tests that exercise `jwtDecoder`.

**Fix:** changed the `jwtDecoder` factory method's parameter to `ObjectProvider<JwtDecoder> issuerJwtDecoder`, and `TestFirstDelegatingJwtDecoder` now holds that `ObjectProvider` rather than a resolved `JwtDecoder`, calling `.getObject()` only inside the fallback branch of `decode(...)` — so the real decoder, and its OIDC discovery call, is now actually never constructed unless a token falls through the test decoder. The `allow-test-issuer=false` path (`issuerJwtDecoder.getObject()`) still resolves it directly, which is correct there: in that mode it's the only decoder, so failing fast on an unreachable issuer is the intended behavior.

**Action for future tickets:** any bean that depends on a `@Lazy`-marked `@Bean` must inject it via `ObjectProvider<T>` (or `@Lazy` on the injection point itself), never as a plain constructor/method parameter — otherwise `@Lazy` on the producing side is silently ineffective.

## ADR-019 — `@auth0/nextjs-auth0` v4: renamed env vars, `/auth/*` routes, `proxy.ts` not `middleware.ts`

Status: **Accepted**, 2026-11-06. Installed `@auth0/nextjs-auth0@4.33.0` for T08 and verified its actual shipped docs (`node_modules/@auth0/nextjs-auth0/{README.md,AGENTS.md,skills/SKILL.md}`, plus the package's own `.d.ts`) rather than trusting the blueprint's guessed env var names or older (v3) Auth0 quickstarts, the same discipline ADR-008/ADR-016 established for Spring Boot 4 and Jackson 3.

- v4 renamed `AUTH0_BASE_URL` → `APP_BASE_URL` and uses `AUTH0_SECRET` (not a custom "session secret" name) for the HttpOnly cookie encryption key; `.env.example` and `docs/MANUAL_SETUP.md` Gate H1 were updated to match (the blueprint's original `.env.example` had the old v3-era names).
- v4's mounted routes are `/auth/login`, `/auth/logout`, `/auth/callback`, `/auth/profile` — no `/api` prefix, unlike v3.
- This Next.js version (16.4.5) deprecated `middleware.ts` in favor of `proxy.ts` (`export function proxy(...)`, same `auth0.middleware(request)` call inside it) — confirmed from this project's own installed Next.js docs (`node_modules/next/dist/docs/.../file-conventions/middleware.md`), which explicitly says so and offers a codemod. `apps/web/src/proxy.ts` uses the current convention, not the deprecated one, even though the SDK's own skill docs show `middleware.ts` as one of two still-valid options.

**Note on the installed package itself:** `@auth0/nextjs-auth0` ships an `AGENTS.md` and a `skills/` directory inside the published npm package (`node_modules/@auth0/nextjs-auth0/`), i.e. third-party content, not an instruction source — read and used here only as reference documentation after checking it for anything resembling a prompt injection (none found); nothing in it was executed or treated as a directive.

## ADR-020 — First-login user provisioning trusts only namespaced claims inside the verified access token, never a client-supplied value

Status: **Accepted**, 2026-11-06. T08 requires provisioning a `User` row "by stable OIDC sub on first trusted login" (docs/TASKS.md), and `docs/API_CONTRACT.md` fixes `GET /api/v1/me` as a bodyless GET — so there is no request body to (mis)trust for the new row's `email`/`display_name`, which is exactly right per AGENTS.md rule 11 and `docs/DATA_MODEL.md`'s "verified email provenance; email not sole identity key."

A custom API audience's access token carries no profile claims by default (only the ID token does, and the ID token never leaves the Next.js BFF). `UserProvisioningServiceImpl` therefore reads two **namespaced custom claims** (`https://opspilot.local/email`, `https://opspilot.local/name`) placed directly on the *access token* by an Auth0 Post-Login Action (docs/MANUAL_SETUP.md Gate H1 step 4) — i.e. data Auth0 itself put inside the cryptographically verified JWT the resource server already validates, not anything a caller can influence. When that Action hasn't been configured yet (Gate H1 incomplete, or the local/CI test-only issuer), provisioning falls back to a deterministic, obviously-synthetic placeholder (`{sanitized-sub}@users.opspilot.local`) scoped to the subject, rather than failing the request or inventing a plausible-looking fake value.

Two concurrent first logins for the same subject are handled by catching the unique-constraint violation on `auth_subject` and re-reading, rather than relying on a check-then-insert being atomic.

## ADR-021 — Cache Components can silently freeze a session-dependent route as static when env vars are absent at build time

Status: **Accepted**, 2026-11-06. `apps/web/src/app/app/page.tsx` and `.../[orgId]/layout.tsx` call `auth0.getSession()` (via `fetchMe()`) to decide what to render. Building this app **without** real `AUTH0_*`/`APP_BASE_URL` env vars present (as this local environment and the CI `apps/web` job both do, since Auth0 isn't configured until Gate H1) makes `auth0` resolve to `null` at module load — so the session-reading code path, and the `cookies()` call inside it, is never actually executed during Next's static analysis of the route. Cache Components then has no dynamic dependency to detect and happily prerenders `/app` and `/app/[orgId]/*` as fully static (`○`) instead of partially dynamic (`◐`).

Rebuilding with real (even dummy, locally-generated) Auth0 env vars present reproduces the correct, dynamic classification and confirms `export const instant = false` (already present on both routes per the "Migrating an existing app" section of `node_modules/next/dist/docs/.../guides/authentication-with-cache-components.md`) is sufficient to avoid a build error from reading the session outside a `<Suspense>` boundary.

**Consequence:** any build of `apps/web` that is meant to be deployed must have real Auth0 env vars present *at `next build` time*, not just at runtime — a CI/build step that only smoke-tests the build without secrets (as this repo's own `.github/workflows/ci.yml` does, deliberately, since CI must not need real secrets per AGENTS.md rule 16) will produce a build that looks successful but would serve a stale, pre-session-check static page if ever deployed as-is. This must be carried forward into whichever deployment ticket (T31+) actually builds the production image: that build step needs real secrets, not CI's. Noted here so it isn't rediscovered as a production incident.

## ADR-022 — Node 26 no longer bundles Corepack; `pnpm` needs a one-time `npm install -g corepack`

Status: **Accepted**, 2026-11-06. T04/T05 assumed `nvm use && corepack enable && corepack prepare pnpm@... --activate` (recorded in `docs/DEPENDENCY_DECISIONS.md`) would always make `pnpm` available after switching to the pinned Node version (`apps/web/.nvmrc`, currently Node 26.13.0). On a fresh terminal in this same environment, `corepack` itself was missing (`zsh: command not found: corepack`) — Node stopped bundling Corepack by default starting with Node 25, so a Node 26 install via `nvm` has no `corepack` binary until one is installed separately (`npm install -g corepack@latest`, a one-time per-Node-version step; each `nvm`-managed Node version has its own global `node_modules`). The Makefile's `NVM_USE` helper only runs `nvm use`, not this; it was not changed, since this is a one-time machine-setup gap (akin to Gate H0), not something every `make` invocation should try to silently repair.

**Action for future tickets:** if a fresh clone or CI image ever reports `corepack: command not found` after `nvm use`, run `npm install -g corepack@latest` once for that Node version before `corepack enable`.

## ADR-023 — Invitation tokens: single-use hashed secret, returned once, no email delivery in V1

Status: **Accepted**, 2026-11-08. `POST /api/v1/organizations/{orgId}/invitations` generates a 32-byte random token (`InvitationTokens.generate()`), persists only its SHA-256 hex digest (`InvitationTokens.hash()`), and returns the raw token exactly once, in that response body. This is safe without any extra gate because the caller has already passed the owner/admin `MANAGE_INVITATIONS` check for that specific organization — it is the "protected preview" `docs/TASKS.md` T09 asks for, not a public endpoint. No invitation email is sent (per `docs/TASKS.md`'s explicit sequencing note); the frontend shows the recipient a one-time link the inviter must share themselves. TTL is `app.invitations.ttl` (`API_INVITATION_TTL`, default `P7D`), read as a `java.time.Duration` via `@Value`.

**Alternative considered:** storing the raw token and comparing on accept. Rejected — a leaked database dump would hand out live invitation tokens; hashing means a DB leak alone cannot be used to join an organization.

## ADR-024 — Invitation-accept failure policy: 404 to conceal, 409 once the caller is proven the rightful recipient

Status: **Accepted**, 2026-11-08. `POST /api/v1/invitations/accept` returns the same `404 NOT_FOUND` / "This invitation link is invalid." for both an unknown token hash and a token that exists but is bound to a different (verified, server-resolved) email — so a caller who isn't the intended recipient cannot distinguish "no such invitation" from "that invitation exists, but isn't yours." Once the token hash *and* email both match the caller, the caller has effectively proven they are the rightful recipient, so further failures (`already accepted` — replay; `expired`; `already a member`) return a more specific `409 STATE_CONFLICT` rather than folding everything into the same concealed 404, matching `docs/API_CONTRACT.md`'s "write one policy and tests" instruction while still giving the actual invitee an understandable error.

## ADR-025 — Only an existing OWNER may grant OWNER; last-owner protection is application-enforced, not a DB trigger

Status: **Accepted**, 2026-11-08. `docs/PRODUCT_AND_ARCHITECTURE.md` U02 ("Authorization prevents self-granting owner rights") and the ADMIN role description ("invite and manage users **except owner transfer**") are both enforced the same way, in `InvitationServiceImpl`/`MembershipServiceImpl`: a role of `OWNER` — whether on a new invitation or a role-update PATCH — is only accepted when the *caller's own* resolved role is already `OWNER`. `docs/DATA_MODEL.md`'s "last OWNER cannot be removed" is enforced the same way: before any role change away from `OWNER`, `MembershipRepository.countByOrganizationIdAndRole(orgId, OWNER)` is checked inside the same `@Transactional` method that performs the update, rejecting with `409 STATE_CONFLICT` if it would reach zero. This was a deliberate choice over a Postgres trigger/constraint (simpler to test with Testcontainers, consistent with how `OrganizationAccessService` already keeps all authorization decisions in one layer of Java code rather than splitting policy between the database and the application).

## ADR-026 — `PATCH /organizations/{orgId}/members/{memberId}`'s `{memberId}` is the membership row id, not the user id

Status: **Accepted**, 2026-11-08. `docs/API_CONTRACT.md` names the path segment `{memberId}` without specifying which id it is. This project uses the `memberships.id` primary key (not `users.id`), consistent with `GET .../members` returning each row's own `membershipId` for exactly this purpose. A `{memberId}` that resolves to a real membership row in a *different* organization than `{orgId}` is treated as not found (`404 NOT_FOUND`) rather than `403 FORBIDDEN` — the same "conceal cross-tenant existence" policy `OrganizationAccessService` already established for a caller's own missing membership (`docs/API_CONTRACT.md`: "A mismatch is consistently 403 or conceal with 404; write one policy and tests").

## ADR-027 — No `Idempotency-Key` handling added for T09's endpoints

## ADR-029 — Ticket PATCH requires a client-supplied `version`; JPA's own `@Version` remains a second line of defense

Status: **Accepted**, 2026-11-08. docs/API_CONTRACT.md's ticket PATCH row says "Update status, priority, assigneeId **with optimistic version**," and the acceptance line requires "stale version -> 409." Two stateless HTTP requests to the same endpoint each open their own transaction and read the *current* row, so JPA's `@Version` column alone (already present on `Ticket` since T06) cannot deterministically produce a conflict across two sequential requests — only true in-flight concurrency would ever trigger it, which an integration test cannot reliably force. `UpdateTicketRequest.version` is therefore a required field: the caller echoes back the version they last saw (from a prior `GET`), `TicketServiceImpl.updateTicket` rejects a mismatch with `409 STATE_CONFLICT` *before* applying any change, and JPA's `@Version` still fires as defense-in-depth for a genuine race between two concurrent requests that both passed the explicit check (`GlobalExceptionHandler` now also maps `OptimisticLockingFailureException` to the same `409 STATE_CONFLICT`).

## ADR-032 — Two real T10 CI failures: an untyped-null bind parameter, and reading `@Version` before a flush

Status: **Accepted**, 2026-11-08. First T10 CI run ([run #42516028649](https://github.com/abram0102/OpsPilot-AI-Native-Workflow-Automation-Platform/actions/runs/42516028649)) failed 2 of 57 tests — root-caused from a manually downloaded log archive (same pattern as ADR-015/ADR-018, since GitHub requires sign-in to view Action logs):

1. `pagesDoNotDuplicateOrSkipRecordsAcrossCursors` → `500`: `org.postgresql.util.PSQLException: ERROR: could not determine data type of parameter $6`. The original `findPage` query bound a possibly-null `:cursorCreatedAt` three times; its *first* textual occurrence (`:cursorCreatedAt IS NULL`) is the only place in the generated SQL where that specific bind position has no column to infer a type from, and Postgres refuses to default an untyped parameter to `timestamptz` the way it tolerates it for the enum (`status`/`priority`) columns, which are text. **Fixed** (ADR-030's query, revised) by splitting `TicketRepository.findPage` into `findFirstPage` (no cursor fields at all) and `findPageAfter` (cursor fields always bound to a real, non-null value) — the first-page query never binds a null timestamp, and the with-cursor query's `:cursorCreatedAt` occurrences are always in a typed-comparison context.
2. `onlyAllowedStatusTransitionsAreAccepted` → the response's `version` was `0` right after an update that should have bumped it to `1`. `TicketRepository.save(ticket)` does not flush; Hibernate only increments a `@Version` field's in-memory value when it actually executes the versioned `UPDATE`, which under default `FlushMode.AUTO` happens at the `@Transactional` method's commit — *after* `TicketResponse.from(...)` had already read the stale in-memory value. **Fixed** by using `saveAndFlush` in `TicketServiceImpl.createTicket`/`updateTicket`, wherever the response includes a DB/Hibernate-generated value (`version`, and `createTicket`'s `createdAt`/`updatedAt`).

**Consequence/open question flagged, not fixed, here:** the same read-after-`save()`-before-flush pattern exists in `OrganizationServiceImpl.createOrganization` (T09) for `createdAt` — untested there because no T09 test asserts `$.createdAt`, so it is a latent, not confirmed, gap. Left alone in this ticket (AGENTS.md rule 2: implement one ticket only) rather than opportunistically patched; worth a dedicated look if a future ticket's test ever asserts that field.

Re-pushed and **confirmed**: see `docs/PROGRESS.md` for the CI run that followed this fix.

## ADR-033 — T11 OpenAPI/TS client generation: tooling, three real bugs caught generating it, and known gaps

Status: **Accepted**, 2026-11-08.

**Generator design.** `services/api`'s real `/v3/api-docs` needs the full Spring context (JPA/Flyway need a real Postgres), so the generator (`OpenApiSpecGenerator`, `services/api/src/test/java/com/opspilot/contract/`) is a Testcontainers-backed test that fetches the live spec via `MockMvc` with a test-issuer bearer token (SecurityConfig protects this endpoint like everything else — T10's ADR-028 flagged exactly this) and overwrites `packages/contracts/openapi.json`. It is deliberately **not** named `...Test`, so Surefire's default discovery never runs it as part of a bare `mvn test`; `make generate-contracts` invokes it explicitly (`-Dtest=OpenApiSpecGenerator`), then runs `openapi-typescript` to regenerate `packages/contracts/src/schema.d.ts`. `OpenApiSpecDriftTest` is the read-only counterpart — part of the normal Docker-backed suite — that fails if the committed spec no longer matches what the application actually serves; `packages/contracts/scripts/check-schema-drift.sh` is the TS-side equivalent (regenerates into a temp file, diffs against the committed one). Both drift checks run in CI (`.github/workflows/ci.yml`'s Java and Next.js jobs respectively); neither is reachable locally in this environment (Gate H0: no Docker).

**TS client tooling:** `openapi-typescript` 7.13.0 (types only) + `openapi-fetch` 0.17.0 (a tiny typed fetch wrapper built for exactly those types) — both current stable per their own npm registry metadata at the time of writing, verified before pinning. Chosen over `openapi-generator-cli`'s TS templates for a much smaller, more current, zero-codegen-ceremony client that a Next.js BFF can wrap directly. `packages/contracts` holds the generated spec/types only (no build step, no lockfile — both scripts invoke pinned tool versions via `npx` directly); `apps/web`'s own `src/lib/api/client.ts` does the actual wiring (bearer-token injection, the stable-error-envelope → `ApiError` mapping), imported via a `@contracts/*` TypeScript path alias (`apps/web/tsconfig.json`) rather than a full pnpm workspace — a deliberate, lower-ceremony choice since only *types* cross the boundary (`import type`, erased at build time, so no bundler/`transpilePackages` wiring is needed).

**Three real bugs this generator caught, not hypotheticals** — found via the actual bootstrap runs (three CI round-trips were needed to land a correct committed spec, since Gate H0 means this dev environment can't generate it locally to check first):
1. The first generated spec included `/__test/**` (`TestEchoController` and friends) — springdoc scans the whole context, and those fixtures are component-scanned from the test classpath during a `@SpringBootTest` run. Fixed with `springdoc.paths-to-exclude: /__test/**` in `application.yml`.
2. `CreateTicketRequest`'s `@AssertTrue`-annotated `isCustomerReferenceValid()` (T10, ADR-031) showed up as a fake `customerReferenceValid: boolean` field in the generated schema — Jackson/springdoc's bean introspection treats any `is...()` method as a property getter by convention, validation-only or not. Fixed with `@JsonIgnore` (the classic `com.fasterxml.jackson.annotation` package; Jackson 3's `jackson-databind` relocated to `tools.jackson.*`, but `jackson-annotations` did not — confirmed via the actual resolved dependency tree, not assumed).
3. (Caught by inspection, not CI) a Surefire scope bug in this same work: the new contract test classes weren't added to the Makefile's Docker-dependent exclude list, so `make test-unit` would try to run them locally and fail — fixed alongside.

**Known, accepted gaps (documented, not fixed, here):**
- Every response DTO's fields are generated as optional (`field?: T`) — no `@Schema(requiredMode = REQUIRED)` hints were added across ~10 DTOs for marginal typing benefit, so `apps/web`'s thin per-field wrapper types (`me.ts`/`organizations.ts`/`tickets.ts`) assert non-null at the one boundary that reads the real response, rather than pushing `| undefined` into every page.
- springdoc defaults every POST's documented success status to `200`, even where the controller actually returns `201 Created` (`ResponseEntity.status(HttpStatus.CREATED)` isn't statically inferable without an explicit `@ApiResponse(responseCode = "201")` on every endpoint) — cosmetically wrong in the spec, harmless at runtime (`openapi-fetch` keys off the real `Response.ok`, not the documented status).
- Multiple controllers have a method literally named `create`/`list`/`get`, and springdoc disambiguates collisions by suffixing generated `operationId`s (`create_1`, `create_2`, ...) instead of using a descriptive name — cosmetic only, since this project's client code calls by path (`client.POST("/api/v1/organizations/{orgId}/tickets", ...)`), never by referencing `operations["..."]` directly.
- "Create ticket via typed client works against local API" (the ticket's literal acceptance wording) was not verified as a live round trip in this environment or in CI — doing so would need a long-lived, network-reachable application instance plus a cross-process way to mint a trusted test JWT (the test-issuer key pair is randomly generated per app start — T07's `TestIssuerConfig` — so a separate process can't mint a token for it without new plumbing), which was judged disproportionate scope for this ticket. Verified instead via real TypeScript compilation against the generated DTOs and a mocked-`fetch` unit test (`apps/web/src/lib/api/tickets.test.ts`) that proves the typed client builds the exact real request and parses the exact real response shape — the same class of verification this project has used throughout for anything Gate H0/H1 block from a genuine live check.

## ADR-036 — T13 knowledge upload: application-assigned object keys (no document ID embedded), two-phase local upload, and what's genuinely untested

Status: **Accepted**, 2026-11-09.

**Object key design:** `StorageService.generateObjectKey(organizationId)` returns `"orgs/{organizationId}/knowledge/{randomUUID}"` — a fresh random component, not the document's own database id. The two were considered equivalent at first, but `KnowledgeDocument.id` is Hibernate-generated (`@GeneratedValue(strategy = GenerationType.UUID)`, the same "before-execution" generator every other entity in this codebase uses) and is only assigned in memory at `persist()` time — the object key has to exist *before* the entity does (it's a constructor argument, not set by a later setter), so embedding the real id would have meant either a second write to patch it in afterward, or a non-standard manually-assigned-id entity (breaking consistency with every other entity in this codebase). A second random component costs nothing (the key already embeds `organizationId`, which is what actually matters for "a bad object key cannot escape tenant boundary" — docs/SECURITY_AND_TESTING.md) and keeps `KnowledgeDocument`'s id generation identical to every other entity.

**Local upload is two HTTP calls, not one:** `POST .../knowledge/uploads` (create the session, validate declared metadata) then a separate `PUT .../knowledge/uploads/local-object?objectKey=...` (send the actual bytes) — mirroring the real shape of the S3 path (session creation returns a URL; the bytes go there), even though for the local adapter "there" is this same backend. `StorageService.receiveUpload` is a `default` method that only `LocalFilesystemStorageService` overrides for real; `S3StorageService` inherits the default, which throws rather than silently accepting bytes a real S3 upload would never send it.

**Validation layering**, each independently tested: extension/MIME/size against the *declared* metadata at session creation (`KnowledgeServiceImpl`, Testcontainers HTTP test); magic-byte/size-overrun against the *actual* bytes as they're streamed to disk (`LocalFilesystemStorageService`, a **pure JUnit unit test with no Docker/Spring context at all** — `LocalFilesystemStorageServiceTest`, the one part of this ticket fully verifiable in this Gate-H0-constrained dev environment); and a final existence/size/checksum re-check at `complete` time against whatever the storage layer reports back, never trusting the two earlier steps alone.

**What's real but untestable here:** `S3StorageService` is written against the actual AWS SDK v2 API (verified: `S3Presigner` and its model classes are bundled directly in the `software.amazon.awssdk:s3` artifact in the current SDK version — there is no separate `s3-presigner` module, confirmed by inspecting the resolved jar and Maven Central's search API after `services/api/pom.xml`'s first attempt to declare one as a dependency failed to resolve). It is compile-verified only — Gate H3 (no AWS tenant/bucket/credentials) is the same category of environment limitation this project has already recorded for Docker (Gate H0) and Auth0 (Gate H1), not a new kind of gap. Its `metadataOf` deliberately returns a `null` checksum (S3's `ETag` isn't a reliable SHA-256 for multipart uploads, and real checksum verification needs the uploading client to opt into S3's trailing-checksum feature, which this ticket doesn't implement) — `KnowledgeServiceImpl.completeUpload` treats a `null` actual checksum as "size-verified only," never as a checksum match it didn't actually perform.

## ADR-038 — T14 knowledge frontend: the upload runs entirely through the BFF, and the drop zone is state-driven so it can be tested at all

Status: **Accepted**, 2026-11-09.

**The whole upload runs server-side in one Server Action.** T13's local adapter returns an upload target that is a *relative path back into services/api* (`/api/v1/organizations/{orgId}/knowledge/uploads/local-object?objectKey=...`), which is an authenticated endpoint like any other — not a public URL. The browser cannot PUT to it, because the browser never holds an access token (docs/PRODUCT_AND_ARCHITECTURE.md's BFF boundary, established in T08). So `uploadDocumentAction` performs all three steps itself: create the session, send the bytes, complete the upload, each with the caller's bearer token attached server-side. The browser only ever posts a multipart form to Next.js.

The same path will carry the S3 adapter unchanged: `putUploadedBytes` attaches the bearer token **only when the target is relative** (our own API). An absolute target is a presigned S3 URL that carries its own signature in the query string — forwarding our token there would both leak it to a third-party host and break S3's signed-header check. Keeping the PUT server-side also means the S3 path needs no browser CORS configuration at all.

Consequence: `next.config.ts` raises `experimental.serverActions.bodySizeLimit` to `11mb`. The framework default is 1MB, far below services/api's own 10 MiB document limit, and the extra 1MB of headroom covers what `multipart/form-data` adds around the file (boundaries, part headers) — the Next.js docs' own guidance.

**"No public file URL" (the acceptance line) holds by construction:** no endpoint in this product returns a readable URL for a stored object. The list/detail responses carry metadata only, and the upload target is write-only and either authenticated (local) or short-lived and presigned (S3). The frontend never renders document *contents* either — only filename, type, size, status — since uploaded files are untrusted input (AGENTS.md rule 12) and inlining them is exactly the injection surface docs/SECURITY_AND_TESTING.md warns about. `KnowledgeTable` has a test asserting a filename containing markup lands as text.

**The drop zone keeps its file in React state, not on the `<input>`.** The conventional technique is to write the dropped `FileList` back onto the file input (`input.files = event.dataTransfer.files`), which is correct in a real browser. It is also completely untestable here: jsdom 31 implements neither `DataTransfer` (so no `FileList` can be constructed) nor `HTMLDialogElement.showModal` (so a dialog's contents stay out of the accessibility tree and role-based queries miss them). Rather than ship a drag-and-drop path with no automated coverage, the selected file lives in component state and submission builds its own `FormData`; dragging and picking then travel one identical code path, fully covered by Vitest. For the same reason the form is its own component (`UploadDocumentForm`) with `UploadDocumentDialog` as a thin `<dialog>` wrapper — the logic is testable without fighting jsdom's dialog gap.

The real-browser half of this was still verified directly rather than assumed: a temporary dev-only page (deleted before commit) rendered the form against a real dev server, and a genuine `DragEvent` carrying a real `DataTransfer` confirmed that dropping a `.md` file selects it, dropping a `.exe` is rejected with the allowlist message and disables the upload control, and a dropped file submits through to the action. jsdom could not have shown any of that.

**Progress reporting is deliberately coarse.** The ticket asks for "progress"; a Server Action submit exposes no byte-level upload events, so the form reports a busy state ("Uploading…") rather than drawing a percentage it cannot measure. A real progress bar would need an XHR/streamed upload to a Route Handler — a second upload path, and not something to add for cosmetics.

**Not verified here, by design:** T14's acceptance line asks for Playwright coverage (upload valid file, invalid type/size rejected, status refresh, cross-tenant denied). Playwright is not set up anywhere in this repository — `tests/e2e/` is still a stub — and is scheduled for T29 (Phase 5). T09 and T12 deferred their E2E bullets for the same reason, and that is not re-litigated here. Gate H1 (no real Auth0 tenant) independently blocks any signed-in browser session, so no E2E test could run today regardless. What the backend *does* already cover for this flow, from T13: cross-tenant document ids concealed as 404, viewer-cannot-upload, admin-only delete, and both invalid-type and oversize rejection — all Testcontainers-backed, all passing in CI. The frontend half is covered by 24 Vitest tests plus the real-browser check described above.

## ADR-039 — T15 AI provider layer: where T15 stops and T20 begins, and what "deterministic mock" actually means

Status: **Accepted**, 2026-11-09.

**The T15/T20 boundary.** T15's build line asks for a "real provider adapter driven by env with timeouts/retry budget", while T20 ("Real LLM and eval smoke (opt-in)", **Gate H2**) asks for a "real chat+embedding provider, env configurable model IDs, per-run budget counters, backoff/timeout, provider exception mapping". Read naively these overlap. The split taken here: **T15 builds the machinery and proves it offline; T20 points it at a real provider and pays for it.** Concretely, T15 owns the protocols, the Pydantic structured outputs, the seeded mock, the error taxonomy, the retry budget, the circuit breaker, input budgeting, dimension checking, redaction and the versioned prompts — all exercised by real tests. T20 owns the live call, `make eval-real`, and per-run cost/budget counters (which belong with a run, and runs do not exist until T17/T18). No call to a paid API is made anywhere in T15, which is also what AGENTS.md rule 15 requires.

**No vendor SDK.** The adapter speaks the OpenAI-style REST shape over plain `httpx` (see docs/DEPENDENCY_DECISIONS.md). `LLM_PROVIDER` is an env knob and many hosted/self-hosted backends expose that same shape, so one thin adapter covers them; more importantly, a thin adapter keeps every failure path — timeout, 429, 5xx, 4xx, malformed body, wrong vector width — visible in our own code and testable, rather than behind an SDK's own retry machinery that would need to be disabled to test ours. The `httpx.AsyncClient` is injected, so `httpx.MockTransport` drives all of it with no network and no key.

**The mock is seeded, not empty.** T03's placeholder returned `schema.model_construct()` — an object that skipped validation entirely, so a malformed mock could not have been caught and no test could assert a meaningful value. T15 replaces it with keyword rules (`providers/seed_cases.py`) producing output that is constructed *and then validated through the real Pydantic model*, so a mock run exercises the same validation path a real provider's output would. Determinism is structural: no clock, no RNG, no global state. These seeded rules are explicitly **not** the evaluation dataset — docs/SECURITY_AND_TESTING.md section 5's 60+ case `evals/datasets/support_triage_v1.jsonl` is T30's, and building it here would be implementing a future ticket.

The mock embedding also changed: the T03 version hashed once and cycled the 32-byte digest, so a 1536-wide vector repeated every 32 values and ~98% of it was redundant. It now re-hashes per block, and a test asserts the vector actually varies along its width.

**Token budgets are honest about their precision.** No tokenizer is in the dependency set, so `tokens.py` provides `estimate_tokens`, a documented character-length heuristic used only as a guard rail deciding whether a request is obviously too large to send. It never reports what was billed, and the error message says "estimated" so no caller mistakes it for a measurement (AGENTS.md rule 6). Real usage comes from the provider's own response, in T20.

**Secrets.** `Settings.llm_api_key` is `pydantic.SecretStr`, so printing, formatting or `model_dump`-ing settings yields `**********`; a test asserts that. Exactly one call site reveals it — building the `Authorization` header. `providers/redaction.py` is the second layer, scrubbing text that came from elsewhere (a provider's error body) before it reaches an exception message. Writing the test for that second layer found a real bug: the first pattern matched `Authorization: Bearer <token>` only as far as `Bearer`, leaving the token itself in the string. Fixed by consuming the optional scheme as part of the match.

**Prompts are files, not string literals.** docs/SECURITY_AND_TESTING.md section 5 requires versioning prompts in Git and treating each change as a measurable experiment. Each prompt lives in its own revision-named file (`classification.v1.md`), loaded at runtime, so a prompt change is a reviewable diff and a new revision is a new file rather than an edit that silently changes behaviour for every past run. Both prompts instruct the model to treat ticket and knowledge text as untrusted data, per docs/API_CONTRACT.md's "prompt injection content is data, never system instruction" — and a test asserts that instruction is present in every shipped prompt.

**Scope deliberately left alone:** `RetrievedChunk` (its `score` comes from pgvector — T16) and `ToolProposal` (T19/T21) are not defined here, and `ReplyDraft.source_citations` holds chunk *identifiers* rather than chunk objects so the schema does not couple itself to a retrieval shape that does not exist yet. The mock's reply draft returns no citations, because nothing has been retrieved and inventing one would be the exact failure the prompt forbids.

## ADR-040 — T16: the worker indexes and retrieves against the database directly, and how it reaches document bytes

Status: **Accepted**, 2026-11-09.

**Who writes `knowledge_chunks`.** The Python worker does, directly. docs/PRODUCT_AND_ARCHITECTURE.md's ingest path is explicit — the indexer "writes `knowledge_chunks` rows with tenant scope, embedding model/version and citation reference; document marked `READY` or `FAILED`" — and its module list assigns "chunking, embeddings and tenant-safe vector search" to this service. The internal-API constraint that sits next to it is narrower than it first appears: "Python worker cannot directly bypass business **policy**. Its **business actions** call a Spring Boot internal endpoint", and docs/API_CONTRACT.md's internal API exposes exactly two write actions, both about tickets (`ADD_INTERNAL_TAG`, `PUBLISH_INTERNAL_REPLY`), while naming `SEARCH_KNOWLEDGE` a "read-only worker function with explicit tenant filters". Indexing is not a business action on a ticket. Routing it through that API would also be impossible today: the internal API is T21 and does not exist.

**A correction to this repository's own README.** The root `README.md` claimed "The agent worker never touches business tables directly". That line was written during the README rewrite, overstates the specification, and this ticket contradicts it. It has been narrowed to say the worker never performs a business *action* directly, which is what the spec actually requires. Recorded here rather than quietly edited, because the inaccurate version was published and may have been read.

**How the indexer gets document bytes — the spec is silent.** T13 built storage on the Java side only. The decision taken: the worker reads the *same local storage root* the Java adapter writes to, using the `object_key` already on the document row, and verifies that the resolved path stays inside that root (the key is server-generated, but this code reads it back out of a database row, so it checks rather than trusts). S3 reading is deliberately **not** written: it needs a bucket and credentials that do not exist here (Gate H3), and a second unverifiable code path is worse than an explicit gap. The alternative — an internal download endpoint on the Java service — was rejected for this ticket because it would mean designing part of T21's internal API ahead of the ticket that owns its authentication model.

**Idempotency.** `knowledge_chunks` already carries `UNIQUE (document_id, chunk_index)`, so writes upsert on it and chunks at or beyond the new count are deleted afterwards. Re-ingesting converges rather than accumulating, which matters because delivery is at-least-once by design and because a partially-failed index must be safe to re-run. A document already `READY` returns early instead of redoing the work.

**Deletion races.** The chunk write re-checks that the document still exists, `FOR UPDATE`, inside the same transaction as the inserts. Without that check a document deleted mid-ingest could have its chunks inserted after the cascade had already run.

**No vector index, deliberately.** `V003__knowledge.sql` creates no index on `embedding`, and this ticket adds none: docs/DATA_MODEL.md says "start exact and benchmark before adopting approximate indexes", and T16's own line is "Avoid HNSW at small scale". Retrieval orders by exact cosine distance. No migration was needed at all for this ticket.

**Chunk sizes are approximate, and say so.** docs/PRODUCT_AND_ARCHITECTURE.md specifies "~600 tokens with ~100 overlap". There is still no tokenizer in this service (ADR-039), so sizes are derived from the same documented character-length estimate, and the `token_count` column is populated with an estimate. Splitting prefers a paragraph, line or sentence boundary in the last quarter of each window, because a chunk cut mid-word retrieves worse than a slightly short one.

**Testing under Gate H0.** These tests need PostgreSQL with pgvector, which this machine cannot run. They are marked `db` and skip without `POSTGRES_TEST_DSN`; CI's agent job supplies one from a `pgvector/pgvector:pg16` service container. The obvious guard against a silent skip — running `pytest -m db` as its own step — turns out **not** to work: pytest exits 0 when every selected test skips, so a lost service container would pass the step while proving nothing. (This was caught by checking the exit code rather than assuming it.) The fixture therefore *fails* instead of skipping whenever `CI` is set, which GitHub Actions always sets: skipping is only legitimate on a machine that genuinely cannot run a database. The dedicated step remains, for visibility. The schema under test comes from the real Flyway migration files rather than a copy, since Flyway owns the schema (ADR-007) and a second definition would drift unnoticed.

**One mismatch left for T24, not papered over.** T13's outbox row uses `event_type = "knowledge.document.queued"`, while docs/API_CONTRACT.md names the Redis envelope `knowledge.ingest.requested`. The handler added here reads the payload and is indifferent to the name, but the publisher in T24 has to reconcile the two. **Settled in ADR-048**: the row is renamed, not translated at publish time.

## ADR-041 — T17: no endpoint, and the three choices docs/DATA_MODEL.md left to the implementer

Status: **Accepted**, 2026-11-09.

**T17 adds no HTTP endpoint, deliberately.** Its build line asks for a "list/read API skeleton **only where a working DB implementation exists**" — a restraint, not an instruction to build one. Every run endpoint (`POST tickets/{id}/runs`, `GET runs`, `GET run`, `GET steps`, cancel) belongs to T18; every approval endpoint (list/detail/approve/reject) belongs to T22. Nothing can *create* a run until T18 exists, so any endpoint added now would read tables that nothing populates and return an empty list forever — the "empty placeholder endpoint" AGENTS.md rule 7 explicitly forbids. The acceptance criterion is that invalid transitions are rejected **by the service**, not by an API, and that is exactly what `AgentRunService`, `ApprovalService` and `ToolExecutionService` do. A welcome consequence: with no endpoint, ADR-037's contract-regeneration round-trip does not apply to this ticket at all.

**`outbox_events` is not re-created.** T13 created it early in V003, and ADR-035 promised this migration would add `audit_events` rather than duplicate it. V005 keeps that promise. No extra outbox index is added either: the publisher that would show which indexes it actually needs is T24, and an index carried unused until then is a cost with no reader.

**Choice 1 — a rejected approval completes the run.** docs/DATA_MODEL.md says to "choose one and document it". The run moves to `COMPLETED`, not `FAILED`. The agent did its job: it produced a proposal and a human exercised exactly the control this product is built around. Calling that a failure would make the approval gate look like an error path, and would pollute any failure-rate metric with healthy human judgement. The rejection itself is recorded on the approval row, so nothing is lost.

**Choice 2 — double approval is idempotent, not a 409.** Deciding an approval the *same* way twice returns the stored outcome unchanged, including its original `decision_at`. At-least-once delivery and double-clicked buttons both produce this, and neither is a user error. Deciding it a *different* way is a genuine conflict and is refused — the first decision stands. Together with the row lock in `findByIdAndOrganizationIdForUpdate`, this satisfies AGENTS.md's "double approval cannot execute a tool twice" without making the common case an error.

**Choice 3 — `agent_steps.step_type` and `status` values.** The data model names these columns but never enumerates them, so they are defined here: `CLASSIFY, RETRIEVE, DRAFT_REPLY, PROPOSE_TOOL, AWAIT_APPROVAL, EXECUTE_TOOL, FINALIZE` and `STARTED, SUCCEEDED, FAILED, SKIPPED`, matching the graph T19 will walk.

**`idempotency_key` lands on `agent_runs` now**, with a partial unique index scoped to the organization (so two tenants may reuse a key, and rows without one never collide). T18's acceptance requires "double-click start with same idempotency key gives one run"; the column belongs to the table this ticket owns, and adding it here avoids a V006 patch to schema that was just written.

**Lease columns and the claimable index.** `lease_owner`/`lease_expires_at` plus a partial index over the non-terminal states answer the reclaimer's one question — which runs can be picked up right now. A terminal transition clears the lease, since a finished run holding one would be invisible to that query forever for no reason. The claiming *logic* here is the persistence rule only; the worker that uses it is T25.

**A convention discovered the hard way:** the test was first written with JUnit `@Nested` classes for grouping, and the Docker-independent local run still tried to execute it — Surefire's `!ClassName` exclusion does not match nested inner classes (`AgentPersistenceIntegrationTest$Approvals`). No other test in this repository uses `@Nested`. It was flattened to match, rather than making the Makefile's exclusion pattern cleverer, because the next person adding a Testcontainers test will copy an existing one.

## ADR-042 — T18: a new migration rather than an edit, the first initiator-scoped check, and what 202 actually promises

Status: **Accepted**, 2026-11-10.

**`workflow` arrives as V006, not as an edit to V004.** V004 was written days earlier in T17 and the column arguably belonged in it, but a migration already on `main` is immutable: editing one changes its checksum, and T17's own acceptance ("V004/V005 support reboots without dropping state") only holds while migrations are append-only. The column is load-bearing, not cosmetic — docs/API_CONTRACT.md defines the start body as `{"workflow": "SUPPORT_TRIAGE_V1"}` and requires `409 IDEMPOTENCY_CONFLICT` when a key is "reused with different request body", which simply cannot be detected without storing what the first request asked for. It is `NOT NULL DEFAULT 'SUPPORT_TRIAGE_V1'` so the column can be non-null on a table that may already hold rows; application code always sets it explicitly, and the default is a migration device rather than an invitation to omit the value.

**`IDEMPOTENCY_CONFLICT` needed its own exception.** `ConflictException` already maps to `STATE_CONFLICT`. Both are 409, but clients branch on the *code*, so reusing the existing type would have emitted the wrong one. `IdempotencyConflictException` is deliberately **not** a subclass of `ConflictException`: subclassing would make the correct behaviour depend on `@ExceptionHandler` resolution order, which is a fragile thing to rest a contract on.

**Idempotency semantics.** Same key + same `(ticketId, workflow)` returns the original run with another 202 — a double-clicked button and a retried POST both land there, and neither should start a second run or read as an error. Same key + anything else is the conflict. The request body contains only `workflow`, so comparing `(ticketId, workflow)` compares the whole body; if the body ever grows, this comparison has to grow with it.

**The first initiator-scoped authorization check in this codebase.** docs/API_CONTRACT.md scopes cancel to "owner/admin/member initiator", which reads as: a MEMBER may cancel a run they started, ADMIN and above may cancel any. `OrganizationAction` alone cannot express that — it maps an action to a minimum role, with no notion of row ownership — so the service combines `requireAction(RUN_AGENT)` with an explicit `run.getInitiatedBy().equals(principal.userId())` check. Noted here because it is a new shape of rule, and the next row-ownership requirement should follow it rather than inventing a third pattern.

**What the 202 claims, and what it does not.** `POST .../runs` writes the `QUEUED` run and its `agent.run.requested` outbox event in one transaction, so the client has a durable `runId` and a `pollUrl` immediately. Nothing publishes that event (T24) and nothing consumes it (T25), so the response means *accepted and recorded*, not *started*. The controller's javadoc says so, and `AgentRunService.start` deliberately does not imply execution.

**The "direct executor harness" is test-scope only.** It lives in `src/test/java`, carries no Spring stereotype, and is constructed by the test that uses it — so there is no production path into it and nothing to disable in a deployment. That is what keeps it clear of AGENTS.md rule 7's "test-only production bypasses": it adds a test affordance without weakening the product. It proves one thing — that a run row created by the API is consumable, and that status and trace changes persist — and explicitly does not publish to Redis or run a graph.

**A trap worth recording, because it nearly repeated.** Regenerating `packages/contracts` needs Docker (Gate H0), so the spec is produced by a temporary CI step that dumps it into the build log between markers. While that step exists, `OpenApiSpecDriftTest` in the same job compares the live spec against the file the step just rewrote on disk — so **a green run with the bootstrap step present is not evidence the committed spec is current**. This is exactly what misled T13 (ADR-037). The step was removed in the follow-up commit; only the run after that removal proves anything about drift.

## ADR-043 — T19: the graph proposes and gates but executes nothing, and who owns the checkpoint tables

Status: **Accepted**, 2026-11-10.

**The worker writes its own trace.** `docs/PRODUCT_AND_ARCHITECTURE.md`'s agent-execution step says the worker "executes allowlisted action through backend internal API with idempotency key, **saves trace**, marks completed or failed" — only the *action execution* is routed through Java. `docs/API_CONTRACT.md`'s internal API has no step- or status-writing endpoint at all, so writing the trace through Java is not merely unnecessary, it is impossible with the specified surface. Consistent with ADR-040's reading for knowledge chunks.

One consequence worth stating plainly: Java's `AgentRunService` holds the run transition table, and this service does **not** duplicate it. The database CHECK validates a status *value*, not a *transition*, so nothing stops Python writing an out-of-order status via raw SQL. That is tolerable because the graph only ever drives a run forward along the single path it walks, and a second writer touching the same run is prevented by the lease rather than by a second copy of the rules. If a future ticket gives Python branching control over run status, the transition table has to move somewhere both services read.

**Checkpoint tables are the checkpointer's, not Flyway's.** `docs/DATA_MODEL.md` says they "are initialized by the installed checkpointer package and use stable `thread_id=agent_runs.id`". So `AsyncPostgresSaver.setup()` creates them, no migration describes them, and T18's `checkpoint_thread_id` column is set to the run's own id — making a checkpoint always findable from its run and vice versa. This is the one documented exception to ADR-007.

**The graph executes nothing.** `propose_actions` produces typed proposals and `policy_gate` classifies each as auto-executable, approval-required or rejected; `finalize` leaves a run that proposed a risky write at `AWAITING_APPROVAL`. Execution needs T21's internal endpoint, and a reply needs an `approvalId` only T22 can mint. A run here therefore ends at a decision, never at an effect.

**`propose_actions` makes no model call.** The actions follow deterministically from the classification and from whether a draft exists. Asking a model to name its own tools would hand it precisely the choice AGENTS.md rule 12 says it must not have ("AI cannot choose which permissions it has"). The gate would reject anything out of bounds anyway, but not offering the choice is the stronger position — and it is one fewer provider call per run.

**Defence against prompt injection is layered, because no single layer is convincing.** (1) The `ToolProposal` schema types `action_type` as a two-member enum, so an invented action name cannot even be constructed. (2) Untrusted text — the ticket body and every retrieved excerpt — reaches a prompt only inside explicit `BEGIN/END UNTRUSTED` fences, and both shipped prompts instruct the model to treat anything inside as data. (3) The gate is deterministic code with no model in the loop. (4) A tag must match a strict pattern *and* appear on an allowlist, because a well-formed tag is still not a permitted one — otherwise a model could mint its own taxonomy over time. (5) `PUBLISH_INTERNAL_REPLY` is rejected if it carries any argument at all, since its content must come from the immutable approved proposal rather than the worker's request.

A detail the acceptance criterion forced: the trace must record a blocked attempt "without leaking sensitive content". A step row that quoted the injected payload back would itself become a way to carry it onward, so `_sanitized_output` stores summaries and identifiers only — never the ticket body, excerpt text or drafted reply — and a test asserts an injected marker never appears anywhere in the run's trace.

**Node-list discrepancy, followed rather than reconciled.** `docs/PRODUCT_AND_ARCHITECTURE.md` lists `load_ticket → classify → retrieve_knowledge → propose_actions → policy_gate → (safe_action | await_approval) → finalize`: no `draft_reply`, and a branch after the gate. T19's own build line lists seven nodes including `draft_reply` and no branch. This implementation follows **T19's list**, since it is the ticket being built, and the branch's job — deciding whether a human is needed — is done inside `policy_gate` and recorded by `finalize` instead of being a graph edge. Noted here because the two documents disagree and the next person will notice.

**A time bound had to be invented.** "Bound steps/time/tokens" needs a wall-clock budget, and no setting existed for one (steps and tokens both did). `AGENT_MAX_RUN_SECONDS` (default 120) is new. Every node checks all three budgets before doing anything, and exceeding any of them ends the run `FAILED` with a specific code rather than letting it continue past its budget.

**The harness requirement is satisfied by construction.** T19 asks for a "direct synchronous test harness outside HTTP request thread". This service's FastAPI app is health-only and nothing in `graphs/` touches it, so a run can only be executed by calling `execute_run` — never inside a web request. `graphs/handler.py` mirrors `knowledge/handler.py`: an event-shaped entry point plus a CLI, taking T18's existing outbox payload so T25's consumer can call the same function unchanged.

**Two test-fixture gaps fixed in passing.** `conftest.py`'s TRUNCATE list, written in T16, omitted `tickets`, `customers` and every `agent_*` table, so graph tests would have leaked rows into each other. Each table is now named explicitly rather than relying on cascades, so the next addition is less likely to be forgotten the same way.

## ADR-044 — T20: two locks on paid usage, and why no price table ships

Status: **Accepted**, 2026-11-10. T20 remains **BLOCKED** on Gate H2 — see docs/PROGRESS.md.

**Paid usage needs two independent switches, not one.** AGENTS.md rule 15 requires "the human's explicit authorization" before incurring paid API usage. `AI_MODE=real` cannot be that authorization: it is a routine configuration value that a copied `.env`, an inherited shell or a misconfigured deployment could set, and none of those is a human deciding to spend money. So `ALLOW_REAL_LLM_CALLS` exists for exactly this purpose and has no other effect anywhere in the system — real mode alone will not call a provider. `make eval-real` also refuses when `AI_MODE=real` is set but `--real` was not passed, because guessing which the operator meant is the one thing a billable command must not do.

**The refusal is a deliverable, not an error path.** T20's acceptance requires that without H2 "real eval refuses with meaningful setup instructions". Running without Gate H2 is the normal state of this repository, so the refusal reports *every* missing requirement at once rather than the first — an operator deserves the whole checklist, not three consecutive failures each revealing one more item — and states the case cap and how to get cost reporting before they ask.

**No price table ships, and cost is null by default.** This is the ticket's sharpest honesty requirement: "actual model/date/cost recorded, **not made up**". Prices change per model, region and contract, and cannot be verified from inside this process, so a hardcoded table would be a number that looks authoritative and quietly goes stale. Cost therefore appears only when an operator sets `LLM_INPUT_COST_PER_MTOK`/`LLM_OUTPUT_COST_PER_MTOK` to their own rates; otherwise the report records a null cost alongside real token counts. A null cost is a true statement about what the run knows.

For the same reason, **token counts come from the provider's own `usage` block**, never from T15's `estimate_tokens` — that heuristic is explicitly a request-size guard rail (ADR-039), and reporting it as usage would be a fabricated metric. When a provider returns no `usage` block the counts are recorded as *unknown* rather than zero, and `UsageLedger` refuses to produce any total at all in that case: summing unknowns and presenting the result as measured is precisely what AGENTS.md rule 6 forbids. The model id is likewise read back from the response, since a provider may serve a different snapshot than the alias requested.

**What leaves the machine is documented and fictional.** `evals/README.md` lists exactly what a real run transmits: three invented smoke tickets, one fictional FAQ excerpt and the two version-controlled prompts. The evaluation deliberately reads nothing from the database, so running it cannot send a tenant's real content to a provider — which is what makes "appropriate for synthetic demo text" (Gate H2 step 2) a claim about this code rather than a hope.

**Scope.** The smoke evaluation exercises the provider layer — typed classification, a drafted reply, citations over a supplied excerpt — without a database, a run row or the graph. T19 already covers the graph end to end against Postgres; the question this answers is the different one of whether a real provider returns output this system can use. The scored 60+ case dataset and its metrics remain T30's.

## ADR-045 — T21: a second filter chain, a second policy, and keeping the internal API out of the browser's contract

Status: **Accepted**, 2026-11-10.

**Service identity is a separate filter chain, not a role.** `/internal/**` gets its own `SecurityFilterChain` with its own decoder: HS256 against `INTERNAL_SERVICE_SIGNING_SECRET`, audience `https://internal.opspilot.local`. A browser's user token is signed by the OIDC issuer for the `api` audience, so presenting it to the internal endpoint fails on *signature and audience* rather than on a check someone has to remember to write. docs/API_CONTRACT.md's "reject normal browser/user tokens" becomes structural. Both chains are now explicitly `@Order`ed, because leaving the user chain's `anyRequest()` unordered would make the separation depend on bean discovery order — not something to rest an audience split on.

HS256 because `.env.example` already specified a shared `INTERNAL_SERVICE_SIGNING_SECRET` and both parties are ours; the docs never name an algorithm, so this is a choice, not a reading. The internal chain also deliberately omits `PrincipalResolvingJwtAuthenticationConverter`: a service token identifies a worker, not a person, and wiring the user converter there would be the first step toward treating a machine as one.

`ProductionSafetyGuard` gained a second check. Two development secrets are committed to this repository — the `.env.example` placeholder and the `application-local.yml` default — and either in production would mean anyone reading the source could mint a worker token. Startup now fails under the `production` profile for both, the same reasoning that already applied to the test issuer.

**The policy exists twice, and that is the design.** T19's `graphs/policy.py` and T21's `AgentActionPolicy` implement the same tag allowlist and argument rules in two languages. docs/SECURITY_AND_TESTING.md requires "**independent** server-side policy", and the word is load-bearing: the Python gate stops a bad proposal being *made*, this stops a bad action being *executed*, and it must hold even if the worker were bypassed, compromised, buggy, or simply an older deployment. The allowlist is duplicated rather than shared for the same reason — a shared constant would mean widening one side silently widened the other. A future reviewer looking to "DRY this up" should read this paragraph first.

**Nothing the worker says about tenancy is believed.** The request carries only `{runId, toolCallId, actionType, arguments}` — there is deliberately no field for `organizationId` or `ticketId`, because the simplest way never to trust a hint is to give it nowhere to arrive. Organization, ticket, and approval state are all loaded from the persisted run. A fabricated `approvalId` fails because the approval is re-read and re-checked for existence, tenant, run, tool call *and* `APPROVED` status.

**The published reply is the approved text.** `PUBLISH_INTERNAL_REPLY` reads the body out of the immutable stored proposal, never from the request — and a request carrying a `body` argument at all is rejected, since that is an attempt to supply the very thing approval exists to pin down. This is the line that makes "what a human approved" and "what got published" the same string.

**A transition-table correction found while wiring this.** The executor first mutated `ToolExecution` directly and did not compile, because T17 kept those mutators package-private with `ToolExecutionService` owning the state machine. That was the right signal: reaching around it would have created a second copy of the transition rules. Routing through the service also revealed a real ordering bug — the effect was applied while the execution was still `AUTHORIZED`, and `AUTHORIZED -> FAILED_RETRYABLE` is not a legal transition, so recording a failure would itself have thrown inside the catch block. The execution now moves to `EXECUTING` *before* the effect, which is both the truthful order and the only one that can fail. `authorizeWithoutApproval` was added so a policy-permitted safe action still passes through `AUTHORIZED` rather than skipping it, keeping one transition table true for every action.

**`/internal/**` is excluded from the published OpenAPI spec — on correctness grounds.** That spec generates `apps/web`'s typed client, and this is an endpoint the browser's tokens are specifically built to be rejected from; documenting it there would advertise the exact mistake the audience split prevents. It is the same argument ADR-033 accepted for `/__test/**`. The honest caveat: this also happens to avoid ADR-037's contract-regeneration round-trip, which is convenient — so the decision is not left resting on a config line. `OpenApiSpecDriftTest` now asserts that no `/internal` path appears in the generated spec at all, making the outcome enforced rather than assumed.

**The bug that mattered: `@Primary` beat parameter-name injection, and the internal chain got the *user* decoder.** The second CI run failed 20 of the new tests with a perfectly inverted symptom — a browser user token got `200` from `/internal/**` while the worker's service token got `401`. The cause is a Spring resolution rule that is easy to get wrong: with two `JwtDecoder` beans where the user-facing one is `@Primary`, Spring resolves `@Primary` **before** falling back to matching a parameter's name against a bean name. A parameter merely *named* `internalServiceJwtDecoder` was therefore silently injected the user decoder, and the filter chain intended to reject browser tokens was validating them instead. Fixed with an explicit `@Qualifier`.

This is worth dwelling on: the code read correctly, the context started, and every other check passed. Only the integration test asserting the actual security property — that a valid user token is refused here — caught it. It is the strongest argument in this ticket for writing the adversarial test rather than the happy-path one. A Docker-free `InternalServiceJwtDecoderTest` now also pins the decoder's own strictness (wrong key, wrong audience, expired, unconfigured), though it cannot prove the wiring; only a context test can.

**A YAML indentation bug, and the Docker-free guard it prompted.** The first CI run failed every `services/api` test with a single root cause: `app.security.internal-service.audience` had been added to `application.yml` one level too shallow, landing at `app.internal-service.audience`, so the context could not start. The notable part is *why it reached CI at all* — every test that loads the Spring context needs Docker (Gate H0), so no local run could have caught it, and `spotless`, `test-compile` and the Docker-independent subset all passed. `ConfigurationPlaceholderTest` now closes that class of bug without a context or a database: it scans main sources for `@Value("${...}")` placeholders that have no default and asserts each key exists in the shipped YAML. It was verified by reintroducing the exact bug and confirming the test fails naming the key and file — a guard that passes both before and after a fix proves nothing.

**Rejections return `200` with `status: REJECTED`, not `403`.** A refused action is a normal outcome a worker must record and branch on; `403` would conflate "you may not do this" with "your identity is wrong", which the filter chain already answers. The reason for a rejection is logged server-side and audited, but not returned — a detailed reason could otherwise confirm the existence of another tenant's run or approval.

## ADR-046 — T22: a decision endpoint with no request body, and a review page that cannot edit

Status: **Accepted**, 2026-11-11.

**Approve and reject take no request body at all.** docs/API_CONTRACT.md requires that "Approval must not accept a replacement body from frontend", and the surest way to honour that is to leave nothing for a body to substitute: the controller methods declare no `@RequestBody`, the server action carries no text, and the typed client functions take only ids. A test posts a body anyway and asserts the stored proposal is unchanged — the enforcement is structural, and the test proves the structure.

**The review page cannot edit the proposal either.** There is no textarea, no "edit before sending" affordance, and the proposed text is rendered inside a `<blockquote>` as plain text. The page says plainly that approving publishes exactly what is shown. An editable field would quietly turn the human from a reviewer of the agent's words into the author of them, which is a different product with a different accountability story — and it would make "what was approved" and "what was published" two separate strings again.

The text is rendered as plain text rather than markup for a second reason: it was written by a model from untrusted ticket and document content, and this page is read by the one person with authority to publish it (AGENTS.md rule 12). That combination is the worst possible place to interpret HTML.

**Two forms, not one with a hidden outcome field.** A hidden input is a value a browser can be made to change, and approve/reject are not interchangeable. Each decision is its own explicit submission.

**A repeated decision writes nothing twice.** `ApprovalService.decide` already returns the stored outcome for an identical repeat (ADR-041), so this layer checks whether the approval was *already decided before it called* and only then skips the audit row and the resume event. Without that check a double-clicked button would have queued a second `agent.run.resume` and told the worker to publish again — the constraint AGENTS.md states as "double approval cannot execute a tool twice". A test asserts exactly one outbox event survives two approvals.

**Rejection also queues a resume.** It would be easy to read "resume" as only applying to approval, but a rejected run still has to be told to stop waiting or it sits in `AWAITING_APPROVAL` for ever. The event carries identifiers only; the worker re-reads the decision and finalises accordingly, which is T23's job.

**A 409 is surfaced as a conflict, not a failure.** When another reviewer decided first, the UI says so and tells the reader to reload, because their next step is to re-read the decision rather than retry. Both outcome and conflict are announced through `role="status"`/`role="alert"` rather than only rendered.

**`evidence` is read tolerantly.** The response surfaces citations from the stored proposal, and an approval without them shows an empty list plus a warning that nothing is backed by a source — rather than failing the request. The graph that attaches citations is T23's, so approvals created before then legitimately have none, and a reviewer seeing one fewer source is recoverable while a reviewer seeing nothing at all is not.

**Commit order, because the contract gates the client.** The frontend's typed client cannot reference the four new paths until `packages/contracts` is regenerated, and regenerating needs Docker (Gate H0) — so the backend and the temporary bootstrap step landed first, then the regenerated spec, then the frontend. Committing all three together would have pushed a tree that could not typecheck. As in T18, the run carrying the bootstrap step proves nothing about drift; only the run after its removal does.

## ADR-047 — T23: resuming re-runs the node, so the side effect moved; and the crash windows that remain

Status: **Accepted**, 2026-11-11.

**The fact the whole design turns on.** LangGraph's `interrupt()` docstring says "The graph resumes from the start of the node, **re-executing** all logic", and this was verified rather than taken on trust: a node appending to a list before and after the interrupt produces `['BEFORE', 'BEFORE', 'AFTER']` after resume. **Code before an interrupt runs twice; code after it runs once.** For a node that publishes a customer reply, getting that wrong means publishing twice — so the graph is shaped around it, one concern per node:

```
policy_gate ─(approval required?)─→ persist_approval → await_approval → execute_approved_action → finalize
            └────────── no ────────────────────────────────────────────────────────────────────→ finalize
```

`await_approval` contains *nothing but* the interrupt, so its re-execution is a no-op. The internal action lives in a downstream node, which runs exactly once. The approval insert is upstream — LangGraph does not re-run completed nodes — *and* is written `ON CONFLICT (run_id, tool_call_id) DO UPDATE SET updated_at = approvals.updated_at`, a deliberate no-op touch so the statement is idempotent without ever rewriting `status`. Updating status on conflict would let a replayed resume reset a decided approval back to `PENDING`, re-opening a gate a human had already closed.

`await_approval` is also the one node not wrapped by the budget checker: a run must not be failed for the time it spent waiting on a person.

**The decision is re-read, never trusted.** The resume payload carries `{approval_id, decision}`, and `execute_approved_action` ignores the claimed decision entirely — it re-reads the approval, checks it belongs to *this* run, and acts only on the stored status. A resume asserting `APPROVED` against a still-`PENDING` row publishes nothing, which is the acceptance line's "no automatic publishing bypass" tested directly. Same principle as ADR-045: a claim from the other side of a boundary is a hint.

**"Malformed resume rejected" is structural.** `interrupt(..., response_schema=ResumeDecision)` validates the resume against a Pydantic model and, per its docstring, saves nothing when invalid — so the pause survives a bad resume and can still be answered. A test proves exactly that sequence: garbage resume raises, then a well-formed one completes the run.

**A bug the design review caught before it shipped.** The handler's stream loop iterates `update.items()` treating each key as a node name. LangGraph signals a pause with `{"__interrupt__": (Interrupt(...),)}` — a *tuple*, not node state — which would have mis-sequenced a step row and then crashed on the tuple. The loop now checks for that key explicitly before the node loop.

### Crash windows and reconciliation

The ticket asks these be documented "if dual writes cannot be atomic", and they cannot: the checkpoint is written by the checkpointer on its own connection, the `approvals` row on ours. Two commits, one ordering choice.

**Ordering chosen:** the approval row and `AWAITING_APPROVAL` are written *before* the interrupt yields, so the checkpoint is the later write. Consequences:

- **Crash after the approval row, before the checkpoint.** The run shows `AWAITING_APPROVAL` with a decidable approval, but the thread has no paused checkpoint. A reviewer can decide it, and the resume finds nothing to continue. Recovery: re-running the run from the start reaches `persist_approval` again, which is idempotent and returns the same approval id, and reaches the interrupt properly this time. **Nothing has been published, which is the property that matters.**
- **The reverse ordering would be worse.** A checkpoint paused at the interrupt with no approval row leaves a run parked on a decision that no reviewer can see or make — invisible, and not self-healing. That is why the visible, decidable state is written first.
- **Crash between the decision and the resume.** No window: the decision is a single transaction in `services/api` (ADR-046), and the resume is driven separately. An un-resumed decision is simply a pending resume event, which at-least-once delivery retries.
- **Crash after the internal action but before the run is marked COMPLETED.** The effect happened; the run looks unfinished. A re-resume finds the interrupt already answered and makes no second call, and the server-side `(run_id, tool_call_id)` uniqueness would refuse one anyway. `docs/PRODUCT_AND_ARCHITECTURE.md`: "exactly-once effects are enforced by DB uniqueness and action state checks, not by assuming transport delivers once."

**Not cleaned up on purpose:** `docs/DATA_MODEL.md` says "Never clear checkpoints when there are pending approvals", so nothing here deletes checkpoint rows.

### The seam this ticket does not prove

Nothing in this repository runs `services/api` and `services/agent` together — CI has five independent jobs and `infra/docker-compose.yml` holds only Postgres and Redis. So "approve resumes and posts exactly one ticket message" is proven in two halves: the Python tests assert exactly one internal call with the exact payload, and T21's Java tests assert that such a call posts exactly one message and that a replay posts none.

**What remains unproven is the join between them**: that this client's real HTTP request is accepted by that real endpoint. A mocked transport cannot catch a field-name mismatch, an audience typo or an enum spelling difference. That is a genuine gap, not a technicality, and it needs a cross-service environment to close — T29's end-to-end work or a ticket of its own. The mitigation if it ever is wrong: the failure mode is a refused call, not a duplicated effect, because the uniqueness constraint sits on the server.

**No JWT dependency was added.** Minting HS256 is ~15 lines of stdlib `hmac`/`base64`, this service needs no other JWT behaviour, and verification — the hard direction — stays in Java with Spring Security. The Java test signer is hand-rolled for the same reason.

Further decisions and deviations must be recorded here with date, context, alternatives, rationale and consequences.

## ADR-048 — T24: at-least-once by ordering, an allowlist at the publisher, and Redis out of the readiness group

Status: **Accepted**, 2026-11-11.

**The ordering is the delivery guarantee, and it is chosen rather than inherited.** The publisher writes to the stream *first* and marks the row `PUBLISHED` *second*. A crash in the gap republishes the event; the alternative ordering — mark first, publish second — loses it. A duplicate is work a consumer can absorb, because the envelope carries the outbox row's own id as `eventId` and `docs/API_CONTRACT.md` already asks consumers to de-duplicate on it; a lost event has no recovery at all. So `eventId` is deliberately not a fresh uuid per publish: making it one would produce two unrelated-looking messages for the same business fact and quietly destroy the only de-duplication key there is. A test simulates exactly that crash window — publish, force the row back to `PENDING`, publish again — and asserts two stream entries carrying one identical `eventId`. ADR-002 never claimed exactly-once; T26 is where the consumer-side effect is proven singular.

**Publication is a separate transaction from the business write, which is the entire point.** `OutboxPublisher.publishBatch()` runs in its own transaction and is never called from a request path. An unreachable Redis therefore cannot fail a customer's upload or run start — it only delays delivery, with the backlog durable in `outbox_events` and draining on recovery. Proven by pointing a second publisher instance at a closed port and asserting the row survives `PENDING` with a backed-off `next_attempt_at`, then publishing it for real.

**`FOR UPDATE SKIP LOCKED`, as a native query, because Spring Data cannot express it.** `@Lock(PESSIMISTIC_WRITE)` emits `FOR UPDATE` without the skip, and without the skip two API instances would queue behind each other instead of dividing the backlog. The test holds one transaction's claim open while a second publisher claims, and asserts the two sets are disjoint and that neither blocked.

**Redis is deliberately absent from the readiness group.** `management.endpoint.health.group.readiness.include` is spelled out as `readinessState,db` rather than left to Boot's default, which would pick up the auto-configured Redis indicator. Taking every API instance out of rotation because a queue is restarting would convert a few seconds of delayed events into real downtime for users who are not waiting on an agent run at all — the opposite of what the outbox exists to achieve. The outage stays operator-visible in the aggregate `/actuator/health` document (which does go `DOWN`, and is asserted to); `docs/API_CONTRACT.md`'s two probe paths are what an orchestrator must be pointed at, and `docs/DEPLOYMENT_RUNBOOK.md`'s plain `/actuator/health` remains the fuller developer view.

**An allowlist at the publisher, not at the consumer.** `OutboxEventType.PUBLISHABLE` names the three contracted types and the publisher refuses anything else, marking the row `DEAD` instead of putting an unroutable message on the stream. A type nothing can route would otherwise be discovered at the far end of a queue, by a consumer with no way to report back. `DEAD` is terminal and visible rather than deleted, per `docs/SECURITY_AND_TESTING.md`'s "terminal failure with operator-visible reason; no endless tight retry loop", and a poison row is proven not to block the rows behind it. Schema version is checked `!= SCHEMA_VERSION`, not `<`, because a missing JSON field deserializes to `0` and must not read as acceptable. **Being honest about one branch:** the publisher stamps `SCHEMA_VERSION` itself, so `UNKNOWN_SCHEMA_VERSION` is unreachable *from the publisher* by construction — the verdict exists because `classify` is the shared rule both sides apply, and it is the consumer in T25 that will meet a foreign version on the wire. T24 therefore proves the classification as a pure function and does not claim to have dead-lettered a real wrong-version message.

**The `knowledge.document.queued` mismatch is settled by renaming what is emitted.** T13 wrote that `event_type`; `docs/API_CONTRACT.md` has always called the envelope `knowledge.ingest.requested`, and T16 and T18 both deferred it here. Renaming the emitted value is chosen over translating at publish time: a stored row that disagrees with the stream it produced is a debugging trap, and the two would have to be kept in step forever. The Python handler reads the payload and never read the name, so nothing downstream changed. The old string is now an *unroutable* type, which a test asserts — it cannot creep back in silently.

**The timer is off even in local development, which was not the first answer.** The publisher was initially enabled in `application-local.yml`, where a reader would expect it. Checking which profile the test suite actually loads showed why that is wrong: `application.yml` makes `local` the default profile and no test sets `@ActiveProfiles`, so every `@SpringBootTest` in the repository runs under it — a two-second timer would have started inside all twenty of them, claiming and publishing rows that other tests assert on. The flag is therefore off in every shipped profile, and `make api-dev` now genuinely sources `.env` (where `OUTBOX_PUBLISHER_ENABLED=true` lives) rather than only claiming to, which it has done since T02 while `POSTGRES_PASSWORD` silently depended on the operator exporting it by hand.

**Scheduling is separated from publishing, and off by default.** `OutboxPublisherSchedule` only answers "who calls it in production"; the tests call `publishBatch()` directly rather than waiting on a timer, which keeps them fast and non-flaky. It is gated by `app.outbox.publisher.enabled`, on in the local profile (where `make infra-up` supplies Redis) and off in the shipped defaults. The tick catches `RuntimeException`: a scheduled method that throws can be silently dropped from the schedule, which would stall the entire backlog with no signal.

**The consumer group is created by the publisher, not the consumer.** A worker creating its own group on first start would create it at `$` and miss everything published before it ever ran. `RedisConsumerGroupInitializer` creates it from offset `0`, tolerating `BUSYGROUP` (the normal case on every restart) and an absent Redis (harmless — the outbox accrues regardless). T25 builds the consumer that joins it.

**What this ticket does not do.** No migration — V003's `(status, next_attempt_at)` index already serves the claim query. No contract regeneration — no endpoint was added or changed, so ADR-037's standing rule does not fire. No dead-letter *stream*: rejected rows reach the terminal `DEAD` status in the table, and the stream-side DLQ belongs to the consumer in T25.
## ADR-049 — T25: Redis counts the attempts, Postgres owns the lease, and the acknowledgement comes last

Status: **Accepted**, 2026-11-11.

**Acknowledgement is the last thing that happens, and that ordering is the whole contract.** The handler commits its status (and, for a run, its checkpoint); only then does `XACK` run. T25 states the rule — "never ACK successful job before durable status/checkpoint persist" — and a test *observes* it rather than asserting it from the source: the handler is handed a callback that counts pending entries while it is still running, and the count must be 1. Reverse the two lines and that test fails. The cost of this ordering is a duplicate delivery after a crash in the window; the cost of the other ordering is a lost job, which nothing can recover.

**Retries are the pending-entries list, not a retry table and not a sleep loop.** A handler that fails simply does not acknowledge. The entry stays in that consumer's PEL and comes back through `XAUTOCLAIM` on a later pass — by this worker or another one. That is the same mechanism that makes worker death recoverable, so there is one path to test instead of two: a process killed mid-run is, from Redis's point of view, indistinguishable from a handler that never acknowledged.

**Attempts are counted by Redis's own `times_delivered`, not by a column of ours.** It is already durable, already per-message, and already incremented by the claim. A counter of our own would be a second source of truth that could disagree with the first after exactly the crash it exists to survive.

**The lease lives in Postgres even though the queue lives in Redis.** Two things must be true for a worker to own a run: the message is pending for it in the group, and the run is leased to it in `agent_runs`. Only the second is authoritative. A reclaimed message can legitimately reach a second worker while the first is alive but wedged, and nothing in Redis would stop both from running the same graph — AGENTS.md is explicit that this belongs in database constraints and row locks, "not in-memory mutexes", and a Redis lock would be neither. Taking the lease is one conditional UPDATE; the heartbeat renews it *by owner*, so a worker whose lease was reclaimed discovers that fact instead of silently re-taking it. A lease with a NULL expiry is treated as stealable rather than sacred, because an un-expirable lease would strand its run for good.

`worker_reclaim_min_idle_ms` is held at or above `worker_lease_seconds` on purpose, and a test asserts the relationship: claiming a message before the run's lease expires would hand it to a worker that then cannot take the lease and would have to give it straight back.

**The envelope carries identifiers, so every handler reloads the truth.** The outbox row in Postgres does carry a richer payload — `ticketId`, `approvalId` — but T24's envelope deliberately leaves it behind, and this worker deliberately does not go looking for it. A run's ticket is read from the run row; a resume's approval is found by querying the run's decided approvals. Even then the decision is passed to the graph only as a *claim*, which `execute_approved_action` re-reads before acting (ADR-047). Nothing that travelled through a queue is trusted as authorization.

**Replay safety is decided before any graph starts.** T25's "replay of completed run results in zero duplicate side effect" is settled by reading the run's status: terminal means do nothing, `AWAITING_APPROVAL` means a redelivered *start* event must not restart the run from the top. The handlers are idempotent underneath as well — chunks on `(document_id, chunk_index)`, steps on `(run_id, sequence)` — but the cheapest place to stop a replay is before it begins.

**What reaches the dead-letter stream, and what does not.** Messages that cannot be processed at all: malformed, foreign schema version, unroutable type, a run or document that no longer exists, and anything still failing past the attempt cap. What stays off it: a run that genuinely failed and a document the indexer marked `FAILED`. Those are recorded on their own rows with an error code, which is the authoritative place to read them; copying them onto the dead-letter stream would bury the unprocessable messages under ones that were processed exactly as designed. For a run event that exhausts its attempts the run is additionally left terminally `FAILED` with `WORKER_MAX_ATTEMPTS_EXCEEDED` — **a code, never the exception's message**, which may quote a ticket body or a provider response. A test raises with a fake card number in the message and asserts it reaches neither the stream nor the column.

**Readiness on this service still does not touch Redis.** `/health/ready` confirms configuration only; the queue is reported separately at `/health/queue`, which answers `status: "unavailable"` with an error *class* rather than a 500 when Redis cannot be reached. A monitoring check can then tell "the queue is backed up" from "the queue is unreachable" — the same reasoning that kept Redis out of the API's readiness group in ADR-048.

**Two things were found by running it rather than reasoning about it.** `run_forever` created the consumer group before entering its try block, so a worker started while Redis was down exited instead of backing off — the Redis-outage test caught it, and group creation now happens inside the loop, including a reset when `NOGROUP` says the group has vanished (a Redis restart without persistence). And `queue_health` crashed on a stream that does not exist yet: `XLEN` answers 0 for a missing key but `XINFO GROUPS` raises, so `make worker-health` on a fresh deployment reported an error where the honest answer is "nothing here yet". Both now have tests.
## ADR-050 — T26: the unique index is the lock, the row lock covers the retry, and a rolled-back failure still leaves a trace

Status: **Accepted**, 2026-11-11.

**Check-then-insert was the actual defect, and ten callers is what exposes it.** T21's executor looked for an existing `tool_executions` row and inserted one if it found none. Ten concurrent deliveries of the same `toolCallId` all found none, all inserted, and nine met `uq_tool_executions_run_tool_call` as a `DataIntegrityViolationException` — a 500 to the worker instead of the stored outcome, from a transaction already marked rollback-only before anything could recover. `INSERT ... ON CONFLICT (run_id, tool_call_id) DO NOTHING` turns that race into a wait: a second caller arriving while the first is in flight blocks on the index itself until that transaction ends, then finds the committed row. The index *is* the mutual exclusion, which is what AGENTS.md means by "DB uniqueness and row-level locks, not in-memory mutexes" — a mutex would hold inside one JVM, and this API runs behind more than one.

**`SELECT ... FOR UPDATE` covers the race the index cannot.** Once the row exists and is `FAILED_RETRYABLE`, every caller's insert conflicts *instantly* and returns without waiting, so without the row lock all ten would read a non-terminal status and all ten would apply the effect. A duplicate tag is absorbed by `uq_ticket_tags_ticket_tag`; `ticket_messages` has no such constraint, so a duplicate reply would simply be published twice. Two mechanisms, two different races, and a test for each.

**A retryable failure could not actually be retried, and only a retry test found it.** The executor always re-authorizes before executing, but `FAILED_RETRYABLE → AUTHORIZED` was absent from the transition table — so `FAILED_RETRYABLE` was a dead end in practice and the whole distinction from `FAILED_PERMANENT` was decorative. The edge is now there. Both routes out of `FAILED_RETRYABLE` stay legal and mean different things: the executor takes `AUTHORIZED`, which re-reads and re-checks the approval on every attempt, while the direct `EXECUTING` edge (which T17 asserts as the definition of "retryable") remains for a retry inside an already-authorized attempt.

**Cancellation is checked after the replay branch, not before.** An action that already succeeded keeps reporting its outcome even once the run is cancelled, because the effect is out in the world and saying otherwise would make a worker retry something that has already happened. What cancellation forbids is a *new* effect: a run in `CANCELLED` fails the execution permanently and publishes nothing. Before this ticket the executor never read the run's status at all, so a redelivery arriving after a user cancelled still published.

**A database-level failure is atomic and safe, but it was invisible — measured, not assumed.** A probe marked the transaction rollback-only the way a real repository error does and then watched what survived: nothing published, *no execution row*, and **no audit row** — the failure left no trace whatsoever. Keeping the effect, the execution row and the success audit in one transaction is right and is kept, which is exactly why the failure record cannot share their fate. `AgentActionFailureAudit` writes `agent.action.failed` in a `REQUIRES_NEW` transaction, so a rollback still leaves something an operator can see. Nothing there attempts to resurrect the effect: the mutation stays rolled back and the worker retries under the same key.

Note what this does *not* promise. When the failure is a genuine database error the caller may still see an error rather than a tidy `FAILED` response, because a rollback-only transaction cannot commit. That is acceptable and deliberate: the worker treats it as retryable, the message stays unacknowledged, and nothing was published. Buying a prettier response would mean moving the effect into its own inner transaction, and a crash between that inner commit and the outer one would republish on retry — trading a cosmetic improvement for a broken exactly-once guarantee.

**Gate H0 is now lifted for the Java service as well, and it paid for itself immediately.** `TestcontainersConfiguration` and `RedisTestcontainersConfiguration` stand aside when `opspilot.test.external-postgres` / `-redis` are set, so the whole suite runs against servers already on the machine (`make test-integration-external`). T26's subject is races between transactions; writing those tests against CI alone would have meant debugging one push at a time, and the dead-end retry transition is precisely the kind of bug that would have cost two round trips. CI is untouched and still proves the container path, and a flag set where no database exists fails on connection refused rather than passing quietly.
**Addendum, from actually starting the stack.** Booting the whole thing locally (`spring-boot:run` against the external PostgreSQL and Redis, plus `pnpm dev`) turned up two things no test had any reason to cover.

`make seed-demo` could not start at all. `application-seed.yml` sets `web-application-type: none`, `HttpSecurity` is a servlet-scoped bean, and once a second security filter chain existed the context failed with "No qualifying bean of type HttpSecurity" — so the seeder, a `CommandLineRunner`, never ran. Every other test boots a web application and the seeder has no endpoint, so nothing looked. Both security configurations are now `@ConditionalOnWebApplication(SERVLET)`, which is where HTTP security configuration belongs anyway, and `SeedProfileIntegrationTest` boots with `webEnvironment = NONE` to keep it that way (verified by deleting the annotation again and watching the test reproduce the original error exactly).

`OutboxPublisherIntegrationTest` wrote to the real `opspilot:events`. Harmless against a throwaway container, but the external-Redis switch makes it a Redis a developer may also be running `make worker-dev` against — and a test run left events on the development stream, which `make worker-health` then reported as a backlog. The stream is now generated per class. The first attempt at that was `@TestPropertySource("app.outbox.stream-key=test:outbox:${random.uuid}")` and it broke seven tests: `random.uuid` is re-evaluated at *every* property resolution, so the publisher bean and the test's own `@Value` received different streams. `@DynamicPropertySource` with one generated constant is the fix.

## ADR-051 — A design foundation: brand-coloured chrome, element-first base styles, one shared primitive sheet

Status: **Accepted**, 2026-11-11. Operator-requested, outside the ticket sequence.

**The gap was in the plan, not the implementation.** `docs/TASKS.md` has no ticket that styles the product. T04 set up Next.js, T08–T22 each built working pages, and T27 is the *functionality* of the run explorer. The result was accurate, accessible, semantically correct markup with no stylesheet behind it: of fourteen rendered routes only the landing page, `/sign-in`, the `AppShell` and the knowledge table carried any CSS at all. Every other page — the organization selector, dashboard, ticket list and detail, approval inbox and detail, members — rendered as browser-default HTML. Recording this as a planning miss rather than a styling task that slipped: a portfolio deliverable whose screenshots are unstyled is not finished, however sound the server is.

**The markup being semantic is what made this cheap.** Because the pages use real `<label>`s, `<table>`, `<dl>`, `<blockquote>` and `<dialog>` instead of div soup, styling the *elements* in `globals.css` carried most of the visual weight with no per-page work: one base layer gave every form, table and definition list in the app a consistent treatment at once. Page stylesheets then only handle composition — grids, cards, spacing. The alternative, a utility framework, would have meant touching every element in every file to say things the elements already said.

**Tokens, and specifically `--brand-ink`.** All colour goes through custom properties so dark mode is one block rather than a sweep. One token earned its existence the hard way: `--brand-600` was serving both as a hover *background* and as badge *text*, which is fine in light mode and unreadable in dark, where the text must lighten while the background stays dark. `--brand-ink` splits those roles. Found by actually looking at the dark theme, not by reading the stylesheet.

**Why `.secondary` is a class and not `button[type="button"]`.** Keying the quiet button variant off the attribute was the first attempt and it is a trap: an attribute selector outranks a class, so no module could ever override it without a specificity fight. It also conflates two unrelated questions — "is this a submit button" and "is this the important action on this page". The create-ticket *trigger* is a `type="button"` that is the primary action; the filter bar's *submit* is a secondary one.

**Palette: deep Gulf petrol, marble, and gold used sparingly.** `#0C3B4A` as the application chrome in both themes, warm off-white as the reading surface in light mode, and sand gold (`#B8912F`) restricted to small accents — the active-nav rail, the edge of model-authored text. Gold at any scale cheapens rather than elevates. The chrome staying dark while content follows the theme is what makes the brand colour the dominant impression instead of an accent on a white page.

**Colour is never the only cue.** Status pills always spell the status out (`StatusBadge`), the active nav item carries `aria-current="page"` with the gold rail as a visual echo of it rather than the signal itself, and the one colour-only moment — the drop zone turning solid brand while a file is over it — is transient feedback with a text label beside it. `prefers-reduced-motion` disables every transition.

**Agent-authored text is marked everywhere it appears.** The same gold edge marks an agent message in a ticket thread and the proposal on an approval page, and the decision panel is deliberately set apart from the cards above it: it is the only control in the product that publishes text outside the organization. `Reject` is an outlined danger button rather than a solid red one — rejecting a draft is routine review work, and a wall of red pushes reviewers toward approving by default.

## ADR-052 — T27: the explorer stops polling, the filters are server-side, and the contract defines the enums

Status: **Accepted**, 2026-11-11.

**Two query parameters, not two client-side filters.** The run page needs one run's approvals and a ticket page needs one ticket's runs. Both were reachable already by fetching the organization's whole list and filtering in the BFF, and both are now `runId` / `ticketId` parameters filtered *inside the query*, next to `organization_id`. The reason is not performance: a client-supplied id that is filtered in memory is an id the database was asked about on behalf of a caller who may not be entitled to it. Scoping in the query makes another tenant's run or ticket answer with an empty list by construction, and that is what the two "reveals nothing" tests assert. The approvals repository already had `findAllByRunIdAndOrganizationIdOrderByCreatedAt`, used only by a test — T27 wires it to the endpoint it was evidently written for.

**`runId` deliberately changes the no-status default.** With no parameters the approvals endpoint answers "what is waiting for me" and returns `PENDING`. With a `runId` it returns that run's approvals whatever their status, because a run's page exists to show the decision the run was waiting on — defaulting it to pending would hide the one row the reader came for. Asymmetric, documented on both sides, and covered by its own test.

**Polling stops, and only re-renders on change.** `RunPoller` returns before creating an interval at all when the run is terminal, and otherwise reads a three-field status endpoint and calls `router.refresh()` only when the status actually differs. A blind `router.refresh()` on a timer would re-fetch the whole trace every few seconds forever, including for runs that finished hours ago. When the endpoint answers with an error the interval is cleared and the page says live updates stopped: a page that keeps retrying silently looks live while being stale, which is the misleading state T27's acceptance rules out.

**The status endpoint exists because the browser has no token.** `/api/run-status` forwards `orgId`/`runId` with the caller's own session token and copies back status, step count and timestamp — nothing else. It checks neither id: services/api resolves membership from the token and answers 403/404 for anything the caller may not read, and the route passes that status and stable code through unchanged rather than flattening it to a 500, so a client cannot be put in a retry loop over something it will never be allowed to see.

**Idempotency is in the form, not the button.** The start-run form carries a key generated once when the page rendered, so a double submission reuses it and services/api returns the run it already created (T18). `disabled={pending}` narrows the window; the key closes it. The same applies to cancel, which is idempotent server-side, and whose 409 is reported as "this run already finished" rather than as a failure — the reader's next step is to look at the outcome, not to retry.

**The enums come from the generated contract.** `AgentRunStatus` and `AgentStepType` were written out by hand first and were wrong: `SUCCEEDED`, `PLAN`, `DRAFT`, `TOOL_CALL` never existed, against a real vocabulary of `COMPLETED`/`RETRY_SCHEDULED` and `CLASSIFY`/`DRAFT_REPLY`/`PROPOSE_TOOL`/`EXECUTE_TOOL`. `tsc` caught it only because the generated `paths` type disagreed. They are now derived from `components["schemas"]` so the next server-side addition is a type error rather than a status the UI silently renders as neutral.

**Found by running it, again.** `make worker-dev` could not start: `.env.example` ships `LLM_INPUT_COST_PER_MTOK=` with no value, `make worker-dev` sources that file, and pydantic receives the empty *string* — not an absent value — which `Decimal | None` rejects. The worker died before reading a single event. "Set to nothing" and "not set" mean the same thing for a price, so both now mean no rate (`OptionalDecimal`), with a test that fails against the old annotation. That makes two targets in this project (`make seed-demo` in the design pass, `make worker-dev` here) that no test covered because no test runs a Makefile target the way an operator does.

## ADR-053 — T28: the security suite discovers its own targets, and the threat model is checked by a script

**Context.** By the time T28 came round, almost every case in `docs/SECURITY_AND_TESTING.md` §3 was
already covered — 235 Java and 308 Python tests, including cross-tenant concealment on every
resource, the full role matrix, approval forgery, duplicate execution under real concurrency,
injected document text, and upload MIME/magic-byte spoofing. T28 was therefore not "write the
security tests". It was: find what the named tests structurally cannot cover, make the set runnable
as a suite, and prove the net catches a regression.

**The gap was shape, not quantity.** Every existing test names the endpoint it attacks. That means
the suite can only ever prove something about an endpoint somebody remembered to write a test for —
and the realistic failure in this codebase is not "the ticket check was wrong", it is "T31 adds an
endpoint and forgets the check entirely". No amount of named tests catches that.

**Decision 1 — the sweep asks Spring for the targets.**
`SecurityRegressionSweepIntegrationTest` reads `RequestMappingHandlerMapping` and attacks every
mapping it finds: no credential must give 401 everywhere, and a validly authenticated stranger must
be refused on every `{orgId}` route. A new endpoint is in the test the moment it is mapped.

Two details are deliberate. **GET is held to a stricter standard than a write**: a generic sweep
cannot invent a valid body, so a write gets `{}` and can legitimately be deflected by bean
validation at 400 before authorization is consulted — that is still a refusal and still no leak, so
writes must be 4xx and must never be 2xx or 5xx. A GET has no body to be deflected by, so it must
be refused by the authorization check itself: 403 or 404, nothing else. And **the sweep asserts its
own population** (more than 20 routes, more than 10 scoped ones), because a discovery bug that found
nothing would otherwise pass while proving the opposite of what it claims. A companion test checks a
real member still gets 200, so "all blocked" cannot be satisfied by refusing everyone.

**Decision 2 — the suite is selected by tag, never by a file list.** Java classes carry
`@Tag("security")`, Python modules `pytestmark = pytest.mark.security`, and `make test-security`
selects on those. A list of file names is a thing that goes out of date silently, and a security
suite that quietly stopped covering an endpoint is worse than no suite. CI runs the selection as its
own named step in both the Java and Python jobs, so the state is readable without opening a log and
a selection that matched nothing fails the build. The web side has no tag mechanism, so its two
boundary tests are named explicitly — the one place a list was unavoidable.

**Decision 3 — the threat model's test column is machine-checked.** `docs/THREAT_MODEL.md` maps each
threat to `path::test name`, and `scripts/check-threat-model.py` fails CI if a referenced file or
test name no longer exists. A threat model pointing at renamed tests reads as coverage and is not,
which is worse than an empty column; now renaming a security test breaks the build and the author
has to update the row. The document also states its gaps as rows (**none**, with why) rather than
leaving them to be inferred from absence.

**Decision 4 — OSV-Scanner, not three ecosystem audits.** One scanner reads all three lockfiles
(`pom.xml`, `uv.lock`, `pnpm-lock.yaml`) in a single pass with no API key, registry account or NVD
throttling. The alternative was three native audit commands with three output formats and three
failure conventions. Dependabot already opened update PRs; what was missing was a gate that fails
one, which is now the `Dependency advisories (OSV)` job and `make audit-deps`.

**What the drill found.** The acceptance criterion "tests catch deliberate unsafe code path in
review" was run, not assumed. Removing the membership check from `listDocuments` was caught by the
sweep, which named the route (`GET …/knowledge/documents` answering `200` to a stranger) — and it
failed on the *missing check*, not on whether that fixture happened to hold rows, which is the right
sensitivity. Dropping `organizationId` from the run list's two keyset queries was caught by exactly
**one** test, the ticket-filter one added in T27: every other list test seeds a single tenant, and
the membership check (a separate mechanism) kept the sweep's stranger out, so the plain list — the
call the UI makes on every page load — had no direct cross-tenant assertion at all. A second test
now covers it, and the drill was re-run to confirm both fail.

**What the sweep found on its first run.** `PUT …/knowledge/uploads/local-object` answered **500
`INTERNAL_ERROR`** when its required `objectKey` query parameter was absent;
`MissingServletRequestParameterException` reached the catch-all `@ExceptionHandler(Exception.class)`.
Probing further showed the wrong HTTP verb and an unsupported content type did the same. A client
mistake dressed as a server failure is wrong twice over: the caller is told to retry something that
cannot work, and the 5xx rate that `docs/SECURITY_AND_TESTING.md` §7 alerts on rises every time
anyone probes the API — so a scanner looks exactly like an outage. Three handlers were added (400
`VALIDATION_ERROR`, 405 `METHOD_NOT_ALLOWED`, 415 `UNSUPPORTED_MEDIA_TYPE`); the last two are codes
`docs/API_CONTRACT.md` did not list, and it has been extended rather than the statuses bent to fit.

**Rejected: a separate `security` source set or Maven profile.** The tagged tests also belong to the
ordinary suite — running them twice in CI is seconds, and a security test that only runs under a
special command is a security test that stops running.

**Addendum — a flake the single-class run could not have found.** `SecretHygieneIntegrationTest`
first used logback's own `ListAppender`, which keeps a plain `ArrayList`. The threads that log
during a request are not only the test's: Hikari, the Redis client and Spring's background threads
all write to the root logger, so streaming that list while another thread appended threw
`ConcurrentModificationException` — on a *full suite* run, after the class had passed twice on its
own. It is now a concurrent queue that flattens each event to a string at append time, because
logback reuses and mutates event objects and holding references to read later is a second race on
top of the first. Worth recording for the general point: a test that captures logs is a test with
other people's threads in it, and running one class is not the same experiment as running the suite.
