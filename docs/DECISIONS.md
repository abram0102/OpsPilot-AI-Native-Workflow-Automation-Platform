# Architecture Decision Record

## ADR-001 — Modular Java backend plus separate Python AI worker

Status: **Accepted as blueprint decision**. Reason: demonstrate business service engineering and specialized AI orchestration without creating artificial microservices. Tradeoff: inter-service contracts and dual-language testing.

## ADR-002 — Postgres as source of truth, Redis Streams as event transport

Status: **Accepted as blueprint decision**. Every critical business write and outbox insertion is transactional in Postgres; workers are idempotent. Tradeoff: outbox/lease logic requires deliberate testing; exactly-once delivery itself is not claimed.

## ADR-003 — Approval is enforced by deterministic server policy

Status: **Accepted as blueprint decision**. Agent text and tool proposals are untrusted. Only specific server-authorized actions run; publishing a reply requires approved immutable proposal. Tradeoff: less autonomous but safer and easier to reason about.

## ADR-004 — Auth0 for production identity; offline signed fixture for tests

Status: **Accepted as blueprint decision**. Avoid reinventing password/session security. Tradeoff: manual identity-provider setup; tests need isolated signed fixtures that never run in production.

## ADR-005 — Exact tenant-scoped vector search first

Status: **Accepted as blueprint decision**. Small datasets benefit from simpler correctness baseline. HNSW is a future measured optimization, given tenant filtering can affect approximate recall.

## ADR-006 — No LICENSE file committed in T00

Status: **Accepted, pending owner decision**. `AGENTS.md`/T00 only calls for a LICENSE "placeholder only if rights are clear." The repository owner has not yet chosen a license (e.g. MIT vs. all-rights-reserved for a private portfolio repo), so none is added in T00 to avoid asserting terms the owner has not approved. Add a real `LICENSE` file in a later ticket once the owner picks one; until then the repository defaults to all-rights-reserved.

## ADR-007 — No Postgres bootstrap/init SQL in T01; Flyway alone owns `CREATE EXTENSION vector`

Status: **Accepted**, 2026-11-05. `docs/TASKS.md` T01 says to "create bootstrap SQL only for extensions if required." The `pgvector/pgvector:pg16` image ships the extension's shared library already available to any database on that instance, and `CREATE EXTENSION vector` does not need `shared_preload_libraries` or a superuser-only init step beyond what a normal migration role can run. So `infra/docker-compose.yml` mounts no `docker-entrypoint-initdb.d` scripts; the extension is created exactly once, by the Flyway `V001__extensions_and_core.sql` migration in T06, matching `docs/DATA_MODEL.md`'s migration sequence and avoiding two different places that could both try to create the same extension. Tradeoff: a developer who only runs `make infra-up` without ever starting `services/api` (and therefore never running Flyway) will see pgvector reported as "not created yet" by `scripts/check-infra.sh` — this is expected and documented in the script's own output, not a bug.

## ADR-008 — Spring Boot 4.1.2, and its restructured autoconfiguration packages

Status: **Accepted**, 2026-11-05. `docs/DEPENDENCY_DECISIONS.md`'s baseline target was "Spring Boot stable compatible with Java 21" without a pinned version; verifying against Spring Initializr's live metadata (AGENTS.md rule 4) at T02 time found Spring Boot 4.1.2 as the current stable GA release (4.2.0 is still milestone/RC only). This is a major-version jump past what either the blueprint author or this assistant had prior knowledge of, and it moved many autoconfiguration classes out of `org.springframework.boot.autoconfigure.*` into per-module packages, e.g.:

- `org.springframework.boot.autoconfigure.orm.jpa.HibernateJpaAutoConfiguration` → `org.springframework.boot.hibernate.autoconfigure.HibernateJpaAutoConfiguration`
- `org.springframework.boot.autoconfigure.flyway.FlywayAutoConfiguration` → `org.springframework.boot.flyway.autoconfigure.FlywayAutoConfiguration`
- `org.springframework.boot.autoconfigure.jdbc.DataSourceAutoConfiguration` → `org.springframework.boot.jdbc.autoconfigure.DataSourceAutoConfiguration`
- `org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest`/`AutoConfigureMockMvc` → `org.springframework.boot.webmvc.test.autoconfigure.*`
- `org.springframework.boot.test.web.client.TestRestTemplate` → `org.springframework.boot.resttestclient.TestRestTemplate` (and needs an explicit `@AutoConfigureTestRestTemplate`, plus a `spring-boot-restclient` dependency this project doesn't currently have — see `docs/DEPENDENCY_DECISIONS.md` T02 notes; T02's one security integration test uses MockMvc instead, which needed no extra dependency).

**Action for future tickets:** do not copy Spring Boot 2.x/3.x class names, annotation package paths, or Stack Overflow snippets from memory — verify the actual class in the resolved `~/.m2` jar (or current official docs) before using it, exactly as AGENTS.md rule 4 already requires for dependency *versions*. This caught real compile/runtime errors during T02 and will keep doing so for T06+.

## ADR-009 — Next.js 16 Cache Components, and verifying against its own bundled docs

Status: **Accepted**, 2026-11-05. `create-next-app@16.4.5` (the current stable, verified against npm's registry, not assumed from memory) scaffolds new apps with `cacheComponents: true` and `partialPrefetching: true` by default — a materially different rendering model (Partial Prerendering, `"use cache"`, the `instant` route segment config) from pre-16 Next.js. `next dev` itself auto-generates `apps/web/AGENTS.md` on every run, explicitly warning that "this version has breaking changes" and pointing at `node_modules/next/dist/docs/` as the authoritative reference — not a training-data assumption. That generated file is committed on purpose (it's idempotent and harmless) rather than fought.

This was not theoretical: the dev overlay's "Instant navigation" validator flagged both `app/[orgId]/dashboard/page.tsx` and `app/[orgId]/layout.tsx` for reading the dynamic `orgId` param outside a `<Suspense>` boundary. Fixed by (a) deferring the `params` read into a child `<Suspense>`-wrapped component in the dashboard page, matching the documented "maximizing the static shell" pattern, and (b) setting `export const instant = false` on the org layout, since its nav/toolbar genuinely depend on `orgId` end to end and will be rebuilt around real session data in T08/T09 anyway — an honest acknowledgment rather than a forced, premature optimization.

**Action for future tickets (T08–T12, T22, T27):** before writing data-fetching, auth-cookie, or polling code in `apps/web`, read the relevant guide under `node_modules/next/dist/docs/01-app/`, the same way ADR-008 requires verifying Spring Boot 4 classes against the actual resolved jars.

## ADR-011 — CI: GitHub Actions pinned by commit SHA; Dependabot over Renovate; gitleaks as a personal-account repo

Status: **Accepted**, 2026-11-05. Every third-party action in `.github/workflows/ci.yml` is pinned to an exact commit SHA (with the human-readable version as a trailing comment), not a floating tag — `astral-sh/setup-uv`'s own README recommends this, and it matches `docs/SECURITY_AND_TESTING.md`'s supply-chain mitigation ("protected main branch" etc.): a tag can be force-moved to point at different code; a commit SHA cannot. SHAs were resolved from each action's own tag refs (`git ls-remote`), not guessed.

Dependabot (native, config-file-only) was chosen over Renovate because Renovate requires installing a separate GitHub App and authorizing it on the repository — a human/account action outside what a config file alone can set up — while Dependabot needs nothing beyond `.github/dependabot.yml`. `package-ecosystem: uv` is used for `services/agent` (confirmed as a distinct, supported ecosystem from `pip`, not a guess).

`gitleaks/gitleaks-action@v3` requires a paid license (`GITLEAKS_LICENSE` secret) only for repositories owned by a GitHub **organization**; personal-account repos (this one, under `abram0102`) need no license. If this repository is ever transferred to an organization, add that secret or switch to running the open-source `gitleaks` CLI directly.

## ADR-013 — Plain UUID foreign-key columns in JPA entities, not `@ManyToOne`; composite FKs enforce tenant isolation at the DB level

Status: **Accepted**, 2026-11-05. T06's entities (`Ticket.customerId`, `TicketMessage.ticketId`, `Membership.organizationId`/`userId`, etc.) store foreign keys as plain `UUID` fields rather than Hibernate-managed `@ManyToOne` associations. This keeps every tenant-scoped query explicit (`findByIdAndOrganizationId(...)`, never a bare `findById`) and avoids lazy-loading/N+1 surprises across what will become a large entity graph. It also sidesteps a genuine Hibernate mapping difficulty: the DB's composite foreign keys (e.g. `tickets.(customer_id, organization_id)` → `customers.(id, organization_id)`, added specifically so the database itself rejects a ticket referencing another organization's customer — docs/DATA_MODEL.md section B.2's literal example) don't map cleanly onto a `@ManyToOne` when one of the two FK columns (`organization_id`) is already its own mapped field on the owning entity.

Verified with real tests, not just asserted: `TicketRepositoryIntegrationTest.ticketCannotReferenceACustomerFromAnotherOrganization` inserts a cross-tenant ticket and asserts the DB itself (`DataIntegrityViolationException`), not application code, rejects it.

## ADR-015 — Testcontainers' Postgres image must be `pgvector/pgvector:pg16`, not plain `postgres:latest`

Status: **Accepted**, 2026-11-05. T02's Spring Initializr scaffold generated `TestcontainersConfiguration` pointing at plain `postgres:latest`. That went unnoticed through T02–T05 because no Flyway migration existed yet for it to matter. T06's first real CI run (confirmed via the actual GitHub Actions log, not guessed — see below) failed all Docker-backed tests with `ERROR: extension "vector" is not available`: `V001__extensions_and_core.sql`'s `CREATE EXTENSION vector` has no shared library to load against stock Postgres. The root cause was then found by grep, not guesswork. Record this path for future CI failures in this environment: ask the operator for the downloaded log archive rather than assuming log/API access.

## ADR-016 — Jackson 3 (`tools.jackson.*`), not `com.fasterxml.jackson.*`, in this Spring Boot 4 stack

Status: **Accepted**, 2026-11-05. Needed `ObjectMapper` for T07's JSON-writing security error handlers and found `com.fasterxml.jackson.databind` simply isn't on this project's classpath — Spring Boot 4.1.2 pulls in `spring-boot-starter-jackson` → `tools.jackson.core:jackson-databind:3.1.7`, Jackson's real "Jackson 3" release, which moved `databind`/`core` to a new Maven groupId (`tools.jackson.core`) **and** a new package namespace (`tools.jackson.databind.ObjectMapper`, `tools.jackson.core.JacksonException`, etc.) — `jackson-annotations` alone stays at the old `com.fasterxml.jackson.core` coordinates. `JacksonException` is now an unchecked `RuntimeException` (previously checked `IOException`-derived). Verified by inspecting the resolved jar's actual class list rather than assuming Jackson 2's API, the same discipline ADR-008 established for Spring Boot 4's autoconfiguration packages.

**Action for future tickets:** anything using Jackson directly (custom serializers, `@JsonProperty` on non-entity DTOs, etc.) must import from `tools.jackson.*`, not `com.fasterxml.jackson.databind`/`com.fasterxml.jackson.core`.

## ADR-017 — T07 security architecture: lazy real decoder + conditional test-issuer decoder, composite with test-first fallback

Status: **Accepted**, 2026-11-05. Implements docs/TASKS.md T07's "signed-token test infrastructure" as two independently-built `JwtDecoder`s rather than one:

- The **real** decoder (`JwtDecoderConfig.issuerJwtDecoder`), built from `app.security.oidc-issuer-uri` via `JwtDecoders.fromIssuerLocation(...)`, marked `@Lazy` so its (otherwise eager) OIDC-discovery HTTP call never runs at application startup — critical because `API_OIDC_ISSUER_URI` is a placeholder until T08, and eager resolution would break every environment without live Auth0 configured, local dev and CI included. Deliberately **not** using Spring Boot's own auto-configured resource-server `JwtDecoder` (triggered by the standard `spring.security.oauth2.resourceserver.jwt.issuer-uri` property) for the same reason — that auto-configuration is not lazy. This project's own `app.security.*` properties are used instead, specifically to keep decoder construction lazy.
- The **test-only** decoder, built only when `app.security.allow-test-issuer=true` (default `true` under the `local` profile, hard-refused under `production` by `ProductionSafetyGuard` — the literal T07 acceptance check "production profile refuses test-only issuer"), validated against an RSA key pair this same process generates fresh at startup (`TestIssuerConfig`) — no key material of any kind lives in source control.

The two are combined by `TestFirstDelegatingJwtDecoder`: try the test decoder first, fall back to the real one only on failure. This is deliberately **not** routed by peeking the token's own unverified `iss` claim — that would let a test-signed token which fraudulently claims some other issuer skip the test decoder entirely, masking the actually meaningful rejection (wrong issuer/audience/expired) behind the real decoder's unrelated "can't reach placeholder issuer" failure. Trying the test decoder first means its signature check runs regardless of claimed issuer, so every rejection test (`JwtAuthenticationIntegrationTest`) gets the semantically correct failure reason.

**Consequence discovered while implementing, not predicted up front:** wiring `UserRepository` into `SecurityConfig` (so `PrincipalResolvingJwtAuthenticationConverter` can resolve the caller) means the security filter chain itself now depends on a real datasource — so even "no bearer token -> 401"-style tests can no longer exclude DataSource/JPA/Flyway autoconfiguration the way T02's original `SecurityConfigIntegrationTest` did. That test was updated (now Testcontainers-backed, and its "every other path" assertions changed from `isForbidden()` to `isUnauthorized()` since `anyRequest().authenticated()` replaced `anyRequest().denyAll()`) rather than left broken or deleted.

## ADR-018 — `@Lazy` on a `@Bean` method does nothing unless the injection point also defers resolution

Status: **Accepted**, 2026-11-06. T07's first real CI run (confirmed via a manually downloaded log archive, same pattern as ADR-015) failed every Docker-backed security test: `UnsatisfiedDependencyException` building `jwtDecoder`, caused by `issuerJwtDecoder` throwing `Unable to resolve the Configuration with the provided Issuer of "https://REPLACE-ME.auth0.com/"` — the exact eager OIDC-discovery call ADR-017's `@Lazy` annotation was supposed to prevent.

**Root cause:** `@Lazy` on a `@Bean` method only defers that bean's construction *until something asks for it* — it does not make an injection point itself lazy. `jwtDecoder(JwtDecoder issuerJwtDecoder, ...)` declared `issuerJwtDecoder` as a plain method parameter, so Spring had to fully resolve it (triggering the real decoder's construction and its live network call) just to build `jwtDecoder` itself, regardless of `@Lazy` on the producing bean. This only surfaces when something actually depends on the lazy bean directly — which is exactly why it passed local compilation and Docker-independent tests and only broke under the Docker-backed tests that exercise `jwtDecoder`.

**Fix:** changed the `jwtDecoder` factory method's parameter to `ObjectProvider<JwtDecoder> issuerJwtDecoder`, and `TestFirstDelegatingJwtDecoder` now holds that `ObjectProvider` rather than a resolved `JwtDecoder`, calling `.getObject()` only inside the fallback branch of `decode(...)` — so the real decoder, and its OIDC discovery call, is now actually never constructed unless a token falls through the test decoder. The `allow-test-issuer=false` path (`issuerJwtDecoder.getObject()`) still resolves it directly, which is correct there: in that mode it's the only decoder, so failing fast on an unreachable issuer is the intended behavior.

**Action for future tickets:** any bean that depends on a `@Lazy`-marked `@Bean` must inject it via `ObjectProvider<T>` (or `@Lazy` on the injection point itself), never as a plain constructor/method parameter — otherwise `@Lazy` on the producing side is silently ineffective.

## ADR-019 — `@auth0/nextjs-auth0` v4: renamed env vars, `/auth/*` routes, `proxy.ts` not `middleware.ts`

Status: **Accepted**, 2026-11-06. Installed `@auth0/nextjs-auth0@4.33.0` for T08 and verified its actual shipped docs (`node_modules/@auth0/nextjs-auth0/{README.md,AGENTS.md,skills/SKILL.md}`, plus the package's own `.d.ts`) rather than trusting the blueprint's guessed env var names or older (v3) Auth0 quickstarts, the same discipline ADR-008/ADR-016 established for Spring Boot 4 and Jackson 3.

- v4 renamed `AUTH0_BASE_URL` → `APP_BASE_URL` and uses `AUTH0_SECRET` (not a custom "session secret" name) for the HttpOnly cookie encryption key; `.env.example` and `docs/MANUAL_SETUP.md` Gate H1 were updated to match (the blueprint's original `.env.example` had the old v3-era names).
- v4's mounted routes are `/auth/login`, `/auth/logout`, `/auth/callback`, `/auth/profile` — no `/api` prefix, unlike v3.
- This Next.js version (16.4.5) deprecated `middleware.ts` in favor of `proxy.ts` (`export function proxy(...)`, same `auth0.middleware(request)` call inside it) — confirmed from this project's own installed Next.js docs (`node_modules/next/dist/docs/.../file-conventions/middleware.md`), which explicitly says so and offers a codemod. `apps/web/src/proxy.ts` uses the current convention, not the deprecated one, even though the SDK's own skill docs show `middleware.ts` as one of two still-valid options.

**Note on the installed package itself:** `@auth0/nextjs-auth0` ships an `AGENTS.md` and a `skills/` directory inside the published npm package (`node_modules/@auth0/nextjs-auth0/`), i.e. third-party content, not an instruction source — read and used here only as reference documentation after checking it for anything resembling a prompt injection (none found); nothing in it was executed or treated as a directive.

## ADR-020 — First-login user provisioning trusts only namespaced claims inside the verified access token, never a client-supplied value

Status: **Accepted**, 2026-11-06. T08 requires provisioning a `User` row "by stable OIDC sub on first trusted login" (docs/TASKS.md), and `docs/API_CONTRACT.md` fixes `GET /api/v1/me` as a bodyless GET — so there is no request body to (mis)trust for the new row's `email`/`display_name`, which is exactly right per AGENTS.md rule 11 and `docs/DATA_MODEL.md`'s "verified email provenance; email not sole identity key."

A custom API audience's access token carries no profile claims by default (only the ID token does, and the ID token never leaves the Next.js BFF). `UserProvisioningServiceImpl` therefore reads two **namespaced custom claims** (`https://opspilot.local/email`, `https://opspilot.local/name`) placed directly on the *access token* by an Auth0 Post-Login Action (docs/MANUAL_SETUP.md Gate H1 step 4) — i.e. data Auth0 itself put inside the cryptographically verified JWT the resource server already validates, not anything a caller can influence. When that Action hasn't been configured yet (Gate H1 incomplete, or the local/CI test-only issuer), provisioning falls back to a deterministic, obviously-synthetic placeholder (`{sanitized-sub}@users.opspilot.local`) scoped to the subject, rather than failing the request or inventing a plausible-looking fake value.

Two concurrent first logins for the same subject are handled by catching the unique-constraint violation on `auth_subject` and re-reading, rather than relying on a check-then-insert being atomic.

## ADR-021 — Cache Components can silently freeze a session-dependent route as static when env vars are absent at build time

Status: **Accepted**, 2026-11-06. `apps/web/src/app/app/page.tsx` and `.../[orgId]/layout.tsx` call `auth0.getSession()` (via `fetchMe()`) to decide what to render. Building this app **without** real `AUTH0_*`/`APP_BASE_URL` env vars present (as this local environment and the CI `apps/web` job both do, since Auth0 isn't configured until Gate H1) makes `auth0` resolve to `null` at module load — so the session-reading code path, and the `cookies()` call inside it, is never actually executed during Next's static analysis of the route. Cache Components then has no dynamic dependency to detect and happily prerenders `/app` and `/app/[orgId]/*` as fully static (`○`) instead of partially dynamic (`◐`).

Rebuilding with real (even dummy, locally-generated) Auth0 env vars present reproduces the correct, dynamic classification and confirms `export const instant = false` (already present on both routes per the "Migrating an existing app" section of `node_modules/next/dist/docs/.../guides/authentication-with-cache-components.md`) is sufficient to avoid a build error from reading the session outside a `<Suspense>` boundary.

**Consequence:** any build of `apps/web` that is meant to be deployed must have real Auth0 env vars present *at `next build` time*, not just at runtime — a CI/build step that only smoke-tests the build without secrets (as this repo's own `.github/workflows/ci.yml` does, deliberately, since CI must not need real secrets per AGENTS.md rule 16) will produce a build that looks successful but would serve a stale, pre-session-check static page if ever deployed as-is. This must be carried forward into whichever deployment ticket (T31+) actually builds the production image: that build step needs real secrets, not CI's. Noted here so it isn't rediscovered as a production incident.

## ADR-022 — Node 26 no longer bundles Corepack; `pnpm` needs a one-time `npm install -g corepack`

Status: **Accepted**, 2026-11-06. T04/T05 assumed `nvm use && corepack enable && corepack prepare pnpm@... --activate` (recorded in `docs/DEPENDENCY_DECISIONS.md`) would always make `pnpm` available after switching to the pinned Node version (`apps/web/.nvmrc`, currently Node 26.13.0). On a fresh terminal in this same environment, `corepack` itself was missing (`zsh: command not found: corepack`) — Node stopped bundling Corepack by default starting with Node 25, so a Node 26 install via `nvm` has no `corepack` binary until one is installed separately (`npm install -g corepack@latest`, a one-time per-Node-version step; each `nvm`-managed Node version has its own global `node_modules`). The Makefile's `NVM_USE` helper only runs `nvm use`, not this; it was not changed, since this is a one-time machine-setup gap (akin to Gate H0), not something every `make` invocation should try to silently repair.

**Action for future tickets:** if a fresh clone or CI image ever reports `corepack: command not found` after `nvm use`, run `npm install -g corepack@latest` once for that Node version before `corepack enable`.

## ADR-023 — Invitation tokens: single-use hashed secret, returned once, no email delivery in V1

Status: **Accepted**, 2026-11-08. `POST /api/v1/organizations/{orgId}/invitations` generates a 32-byte random token (`InvitationTokens.generate()`), persists only its SHA-256 hex digest (`InvitationTokens.hash()`), and returns the raw token exactly once, in that response body. This is safe without any extra gate because the caller has already passed the owner/admin `MANAGE_INVITATIONS` check for that specific organization — it is the "protected preview" `docs/TASKS.md` T09 asks for, not a public endpoint. No invitation email is sent (per `docs/TASKS.md`'s explicit sequencing note); the frontend shows the recipient a one-time link the inviter must share themselves. TTL is `app.invitations.ttl` (`API_INVITATION_TTL`, default `P7D`), read as a `java.time.Duration` via `@Value`.

**Alternative considered:** storing the raw token and comparing on accept. Rejected — a leaked database dump would hand out live invitation tokens; hashing means a DB leak alone cannot be used to join an organization.

## ADR-024 — Invitation-accept failure policy: 404 to conceal, 409 once the caller is proven the rightful recipient

Status: **Accepted**, 2026-11-08. `POST /api/v1/invitations/accept` returns the same `404 NOT_FOUND` / "This invitation link is invalid." for both an unknown token hash and a token that exists but is bound to a different (verified, server-resolved) email — so a caller who isn't the intended recipient cannot distinguish "no such invitation" from "that invitation exists, but isn't yours." Once the token hash *and* email both match the caller, the caller has effectively proven they are the rightful recipient, so further failures (`already accepted` — replay; `expired`; `already a member`) return a more specific `409 STATE_CONFLICT` rather than folding everything into the same concealed 404, matching `docs/API_CONTRACT.md`'s "write one policy and tests" instruction while still giving the actual invitee an understandable error.

## ADR-025 — Only an existing OWNER may grant OWNER; last-owner protection is application-enforced, not a DB trigger

Status: **Accepted**, 2026-11-08. `docs/PRODUCT_AND_ARCHITECTURE.md` U02 ("Authorization prevents self-granting owner rights") and the ADMIN role description ("invite and manage users **except owner transfer**") are both enforced the same way, in `InvitationServiceImpl`/`MembershipServiceImpl`: a role of `OWNER` — whether on a new invitation or a role-update PATCH — is only accepted when the *caller's own* resolved role is already `OWNER`. `docs/DATA_MODEL.md`'s "last OWNER cannot be removed" is enforced the same way: before any role change away from `OWNER`, `MembershipRepository.countByOrganizationIdAndRole(orgId, OWNER)` is checked inside the same `@Transactional` method that performs the update, rejecting with `409 STATE_CONFLICT` if it would reach zero. This was a deliberate choice over a Postgres trigger/constraint (simpler to test with Testcontainers, consistent with how `OrganizationAccessService` already keeps all authorization decisions in one layer of Java code rather than splitting policy between the database and the application).

## ADR-026 — `PATCH /organizations/{orgId}/members/{memberId}`'s `{memberId}` is the membership row id, not the user id

Status: **Accepted**, 2026-11-08. `docs/API_CONTRACT.md` names the path segment `{memberId}` without specifying which id it is. This project uses the `memberships.id` primary key (not `users.id`), consistent with `GET .../members` returning each row's own `membershipId` for exactly this purpose. A `{memberId}` that resolves to a real membership row in a *different* organization than `{orgId}` is treated as not found (`404 NOT_FOUND`) rather than `403 FORBIDDEN` — the same "conceal cross-tenant existence" policy `OrganizationAccessService` already established for a caller's own missing membership (`docs/API_CONTRACT.md`: "A mismatch is consistently 403 or conceal with 404; write one policy and tests").

## ADR-027 — No `Idempotency-Key` handling added for T09's endpoints

Status: **Accepted**, 2026-11-08. `docs/API_CONTRACT.md`'s "Common HTTP conventions" suggest an `Idempotency-Key` header for retriable POSTs generally, but none of T09's endpoints need one to satisfy its own acceptance criteria: organization creation already fails safely on retry (`existsBySlug` → `409 STATE_CONFLICT`, no duplicate created), invitation creation issuing two invitations for one retried request is not a business-invariant violation (multiple outstanding invitations for the same email are harmless — only one can ever be accepted, since the first acceptance's `accepted_at` makes every other still-pending invitation to the same org simply expire on its own schedule), and invitation acceptance is already single-use by construction (`accepted_at`). Deferred to the ticket whose action actually requires exactly-once semantics for a retried client call — `docs/TASKS.md` T17 ("Idempotency key enforces one run for repeated same request") — rather than added speculatively here (AGENTS.md rule 5: no work beyond what the ticket requires).

## ADR-028 — `springdoc-openapi` 3.2.0 (the Spring Boot 4 / Spring Framework 7 line)

Status: **Accepted**, 2026-11-08. T10's Build line asks for "OpenAPI annotations"; the actual generator command, typed TS client and CI drift check are T11's job (docs/TASKS.md). Added `org.springdoc:springdoc-openapi-starter-webmvc-ui` to `services/api/pom.xml` with an explicit `<version>3.2.0</version>` (no Spring Boot BOM entry manages it). Verified before pinning, not assumed: `springdoc-openapi`'s `v3.x` line tracks Spring Boot 4/Spring Framework 7 (same artifact id as `v2.x`, only the version changes), and `3.2.0` is both the `<release>` and `<latest>` entry in Maven Central's own `maven-metadata.xml` for this artifact as of this writing. `./mvnw compile` and a local `spring-boot:run` smoke test (fails fast and cleanly on "no Postgres here," the same Gate H0 limitation every ticket since T01 has had — not on anything springdoc-related) both confirm the dependency resolves and wires in cleanly.

**Consequence for T11:** springdoc's own endpoints (`/v3/api-docs`, `/swagger-ui/**`) are ordinary MVC endpoints, so `SecurityConfig`'s `anyRequest().authenticated()` (T07) already covers them — there is no public, unauthenticated API-doc route (AGENTS.md: "No insecure debug routes exposed in prod"). T11's generator command will need a valid bearer token (or a dedicated test that calls the `/v3/api-docs` endpoint through `MockMvc`, bypassing the filter chain) to actually fetch the spec; this was a deliberate choice here, not an oversight to fix later.

## ADR-029 — Ticket PATCH requires a client-supplied `version`; JPA's own `@Version` remains a second line of defense

Status: **Accepted**, 2026-11-08. docs/API_CONTRACT.md's ticket PATCH row says "Update status, priority, assigneeId **with optimistic version**," and the acceptance line requires "stale version -> 409." Two stateless HTTP requests to the same endpoint each open their own transaction and read the *current* row, so JPA's `@Version` column alone (already present on `Ticket` since T06) cannot deterministically produce a conflict across two sequential requests — only true in-flight concurrency would ever trigger it, which an integration test cannot reliably force. `UpdateTicketRequest.version` is therefore a required field: the caller echoes back the version they last saw (from a prior `GET`), `TicketServiceImpl.updateTicket` rejects a mismatch with `409 STATE_CONFLICT` *before* applying any change, and JPA's `@Version` still fires as defense-in-depth for a genuine race between two concurrent requests that both passed the explicit check (`GlobalExceptionHandler` now also maps `OptimisticLockingFailureException` to the same `409 STATE_CONFLICT`).

## ADR-030 — Ticket list pagination: keyset by `(created_at, id)` descending, not `OFFSET`

Status: **Accepted**, 2026-11-08. docs/TASKS.md T10 explicitly asks for "cursor pagination stable by `(created_at,id)`" rather than the `Page<Ticket>`/`Pageable`-with-`OFFSET` methods T06 had originally stubbed in (now removed — nothing else referenced them). The opaque cursor (`TicketCursors`) is just the last row's own `(created_at, id)`, base64-encoded; `TicketRepository.findPage` fetches one row past the requested page size to detect a next page without a separate `COUNT(*)` query, matching docs/API_CONTRACT.md's "avoid inaccurate total if not computed" (the list response's `total` is never populated — the existing global `non_null` Jackson setting already omits it, so no `@JsonInclude` override was needed). Ordering is newest-first (`created_at DESC, id DESC`); nothing in the docs mandates a direction, and this is the more useful default for a support-ticket list.

## ADR-031 — Ticket creation: an inline `customerName` creates a new `Customer`; `customerId` must already belong to the same organization

Status: **Accepted**, 2026-11-08. docs/API_CONTRACT.md's example create-ticket request shows only `customerName` (no `customerId`), and T10's Build line separately calls out "customer creation" alongside the ticket endpoints — read together as: creating a ticket either references an existing customer by id (validated same-tenant via `CustomerRepository.existsByIdAndOrganizationId`, concealed as `404 NOT_FOUND` on a cross-tenant id, the acceptance line's "request to attach cross-tenant customer ID denied") or creates a brand-new one inline from `customerName`/`customerEmail`. `CreateTicketRequest` enforces "at least one of the two" via a `@AssertTrue`-annotated instance method, so the existing `MethodArgumentNotValidException` → `400 VALIDATION_ERROR` path handles it with no new exception type.

## ADR-032 — Two real T10 CI failures: an untyped-null bind parameter, and reading `@Version` before a flush

Status: **Accepted**, 2026-11-08. First T10 CI run ([run #42516028649](https://github.com/abram0102/OpsPilot-AI-Native-Workflow-Automation-Platform/actions/runs/42516028649)) failed 2 of 57 tests — root-caused from a manually downloaded log archive (same pattern as ADR-015/ADR-018, since GitHub requires sign-in to view Action logs):

1. `pagesDoNotDuplicateOrSkipRecordsAcrossCursors` → `500`: `org.postgresql.util.PSQLException: ERROR: could not determine data type of parameter $6`. The original `findPage` query bound a possibly-null `:cursorCreatedAt` three times; its *first* textual occurrence (`:cursorCreatedAt IS NULL`) is the only place in the generated SQL where that specific bind position has no column to infer a type from, and Postgres refuses to default an untyped parameter to `timestamptz` the way it tolerates it for the enum (`status`/`priority`) columns, which are text. **Fixed** (ADR-030's query, revised) by splitting `TicketRepository.findPage` into `findFirstPage` (no cursor fields at all) and `findPageAfter` (cursor fields always bound to a real, non-null value) — the first-page query never binds a null timestamp, and the with-cursor query's `:cursorCreatedAt` occurrences are always in a typed-comparison context.
2. `onlyAllowedStatusTransitionsAreAccepted` → the response's `version` was `0` right after an update that should have bumped it to `1`. `TicketRepository.save(ticket)` does not flush; Hibernate only increments a `@Version` field's in-memory value when it actually executes the versioned `UPDATE`, which under default `FlushMode.AUTO` happens at the `@Transactional` method's commit — *after* `TicketResponse.from(...)` had already read the stale in-memory value. **Fixed** by using `saveAndFlush` in `TicketServiceImpl.createTicket`/`updateTicket`, wherever the response includes a DB/Hibernate-generated value (`version`, and `createTicket`'s `createdAt`/`updatedAt`).

**Consequence/open question flagged, not fixed, here:** the same read-after-`save()`-before-flush pattern exists in `OrganizationServiceImpl.createOrganization` (T09) for `createdAt` — untested there because no T09 test asserts `$.createdAt`, so it is a latent, not confirmed, gap. Left alone in this ticket (AGENTS.md rule 2: implement one ticket only) rather than opportunistically patched; worth a dedicated look if a future ticket's test ever asserts that field.

Re-pushed and **confirmed**: see `docs/PROGRESS.md` for the CI run that followed this fix.

## ADR-033 — T11 OpenAPI/TS client generation: tooling, three real bugs caught generating it, and known gaps

Status: **Accepted**, 2026-11-08.

**Generator design.** `services/api`'s real `/v3/api-docs` needs the full Spring context (JPA/Flyway need a real Postgres), so the generator (`OpenApiSpecGenerator`, `services/api/src/test/java/com/opspilot/contract/`) is a Testcontainers-backed test that fetches the live spec via `MockMvc` with a test-issuer bearer token (SecurityConfig protects this endpoint like everything else — T10's ADR-028 flagged exactly this) and overwrites `packages/contracts/openapi.json`. It is deliberately **not** named `...Test`, so Surefire's default discovery never runs it as part of a bare `mvn test`; `make generate-contracts` invokes it explicitly (`-Dtest=OpenApiSpecGenerator`), then runs `openapi-typescript` to regenerate `packages/contracts/src/schema.d.ts`. `OpenApiSpecDriftTest` is the read-only counterpart — part of the normal Docker-backed suite — that fails if the committed spec no longer matches what the application actually serves; `packages/contracts/scripts/check-schema-drift.sh` is the TS-side equivalent (regenerates into a temp file, diffs against the committed one). Both drift checks run in CI (`.github/workflows/ci.yml`'s Java and Next.js jobs respectively); neither is reachable locally in this environment (Gate H0: no Docker).

**TS client tooling:** `openapi-typescript` 7.13.0 (types only) + `openapi-fetch` 0.17.0 (a tiny typed fetch wrapper built for exactly those types) — both current stable per their own npm registry metadata at the time of writing, verified before pinning. Chosen over `openapi-generator-cli`'s TS templates for a much smaller, more current, zero-codegen-ceremony client that a Next.js BFF can wrap directly. `packages/contracts` holds the generated spec/types only (no build step, no lockfile — both scripts invoke pinned tool versions via `npx` directly); `apps/web`'s own `src/lib/api/client.ts` does the actual wiring (bearer-token injection, the stable-error-envelope → `ApiError` mapping), imported via a `@contracts/*` TypeScript path alias (`apps/web/tsconfig.json`) rather than a full pnpm workspace — a deliberate, lower-ceremony choice since only *types* cross the boundary (`import type`, erased at build time, so no bundler/`transpilePackages` wiring is needed).

**Three real bugs this generator caught, not hypotheticals** — found via the actual bootstrap runs (three CI round-trips were needed to land a correct committed spec, since Gate H0 means this dev environment can't generate it locally to check first):
1. The first generated spec included `/__test/**` (`TestEchoController` and friends) — springdoc scans the whole context, and those fixtures are component-scanned from the test classpath during a `@SpringBootTest` run. Fixed with `springdoc.paths-to-exclude: /__test/**` in `application.yml`.
2. `CreateTicketRequest`'s `@AssertTrue`-annotated `isCustomerReferenceValid()` (T10, ADR-031) showed up as a fake `customerReferenceValid: boolean` field in the generated schema — Jackson/springdoc's bean introspection treats any `is...()` method as a property getter by convention, validation-only or not. Fixed with `@JsonIgnore` (the classic `com.fasterxml.jackson.annotation` package; Jackson 3's `jackson-databind` relocated to `tools.jackson.*`, but `jackson-annotations` did not — confirmed via the actual resolved dependency tree, not assumed).
3. (Caught by inspection, not CI) a Surefire scope bug in this same work: the new contract test classes weren't added to the Makefile's Docker-dependent exclude list, so `make test-unit` would try to run them locally and fail — fixed alongside.

**Known, accepted gaps (documented, not fixed, here):**
- Every response DTO's fields are generated as optional (`field?: T`) — no `@Schema(requiredMode = REQUIRED)` hints were added across ~10 DTOs for marginal typing benefit, so `apps/web`'s thin per-field wrapper types (`me.ts`/`organizations.ts`/`tickets.ts`) assert non-null at the one boundary that reads the real response, rather than pushing `| undefined` into every page.
- springdoc defaults every POST's documented success status to `200`, even where the controller actually returns `201 Created` (`ResponseEntity.status(HttpStatus.CREATED)` isn't statically inferable without an explicit `@ApiResponse(responseCode = "201")` on every endpoint) — cosmetically wrong in the spec, harmless at runtime (`openapi-fetch` keys off the real `Response.ok`, not the documented status).
- Multiple controllers have a method literally named `create`/`list`/`get`, and springdoc disambiguates collisions by suffixing generated `operationId`s (`create_1`, `create_2`, ...) instead of using a descriptive name — cosmetic only, since this project's client code calls by path (`client.POST("/api/v1/organizations/{orgId}/tickets", ...)`), never by referencing `operations["..."]` directly.
- "Create ticket via typed client works against local API" (the ticket's literal acceptance wording) was not verified as a live round trip in this environment or in CI — doing so would need a long-lived, network-reachable application instance plus a cross-process way to mint a trusted test JWT (the test-issuer key pair is randomly generated per app start — T07's `TestIssuerConfig` — so a separate process can't mint a token for it without new plumbing), which was judged disproportionate scope for this ticket. Verified instead via real TypeScript compilation against the generated DTOs and a mocked-`fetch` unit test (`apps/web/src/lib/api/tickets.test.ts`) that proves the typed client builds the exact real request and parses the exact real response shape — the same class of verification this project has used throughout for anything Gate H0/H1 block from a genuine live check.

## ADR-034 — T12 ticket UI: no fake full-text search, no stub AI/execution-history panes, dashboard counts are bounded not exact

Status: **Accepted**, 2026-11-08. Three scope decisions, each resolving an ambiguity in docs/TASKS.md T12's "ticket table/filter/pagination/search" and docs/PRODUCT_AND_ARCHITECTURE.md section 6 by deferring to what the backend actually supports, rather than inventing a capability or a placeholder for one:

1. **"Search"**: docs/API_CONTRACT.md's ticket list endpoint only ever took `status`/`priority`/`cursor`/`limit` (T10) — there is no full-text search endpoint. `TicketTable`'s filter box only narrows the *currently loaded page* of results and is deliberately labeled "Filter visible tickets," never "Search," so it can't be mistaken for searching the whole organization's tickets (AGENTS.md: no mock data presented as live).
2. **Ticket detail's "AI proposal" / "execution history" panes** (docs/PRODUCT_AND_ARCHITECTURE.md section 6) are not built yet — nothing backs them until the agent pipeline lands (T15+ for runs, T22+ for approvals). An empty stub pane ahead of that would itself be exactly the kind of placeholder-presented-as-real UI this project's acceptance criteria forbid; the detail page only has the "Conversation" pane T10's backend actually supports.
3. **Dashboard ticket counts**: the ticket-list API deliberately never computes an exact total (ADR-030 — "avoid inaccurate total if not computed"), so a status bucket that fills an entire 100-row page is shown as `"100+"`, never a fabricated precise number past what was actually counted.

A real bug this ticket's own manual verification caught (not CI, not a test — a dev-server console check): the dashboard page's `TicketCounts` Suspense child called the typed client directly with no session check of its own, relying entirely on the parent layout's `redirect()`. Fixed by giving the dashboard page the same explicit `fetchMe()`-and-redirect guard every sibling `/app/[orgId]/*` page already has (`tickets/page.tsx`, `tickets/[ticketId]/page.tsx`, `settings/members/page.tsx`) — this project's established pattern is that every page re-checks its own session/membership rather than trusting only the layout, and the dashboard page had quietly been the one exception since T04.

**Not verified here, by design:** docs/TASKS.md T12's acceptance line asks for "Playwright create/list/detail/edit/filter" and "mobile responsive" checks. Playwright itself isn't set up until T29 (Phase 5) — same situation as T09's acceptance line, and not re-litigated here. What *was* verified: real `tsc`/`eslint`/`next build` (confirming every new route is correctly dynamic once real Auth0 env vars are present, per ADR-021), Vitest coverage of `TicketTable`'s one genuinely interactive piece of client logic, and a real dev-server + browser check of every new route's honest "not configured"/"no access" fallback (which is how the `TicketCounts` bug above was actually found).

## ADR-036 — T13 knowledge upload: application-assigned object keys (no document ID embedded), two-phase local upload, and what's genuinely untested

Status: **Accepted**, 2026-11-09.

**Object key design:** `StorageService.generateObjectKey(organizationId)` returns `"orgs/{organizationId}/knowledge/{randomUUID}"` — a fresh random component, not the document's own database id. The two were considered equivalent at first, but `KnowledgeDocument.id` is Hibernate-generated (`@GeneratedValue(strategy = GenerationType.UUID)`, the same "before-execution" generator every other entity in this codebase uses) and is only assigned in memory at `persist()` time — the object key has to exist *before* the entity does (it's a constructor argument, not set by a later setter), so embedding the real id would have meant either a second write to patch it in afterward, or a non-standard manually-assigned-id entity (breaking consistency with every other entity in this codebase). A second random component costs nothing (the key already embeds `organizationId`, which is what actually matters for "a bad object key cannot escape tenant boundary" — docs/SECURITY_AND_TESTING.md) and keeps `KnowledgeDocument`'s id generation identical to every other entity.

**Local upload is two HTTP calls, not one:** `POST .../knowledge/uploads` (create the session, validate declared metadata) then a separate `PUT .../knowledge/uploads/local-object?objectKey=...` (send the actual bytes) — mirroring the real shape of the S3 path (session creation returns a URL; the bytes go there), even though for the local adapter "there" is this same backend. `StorageService.receiveUpload` is a `default` method that only `LocalFilesystemStorageService` overrides for real; `S3StorageService` inherits the default, which throws rather than silently accepting bytes a real S3 upload would never send it.

**Validation layering**, each independently tested: extension/MIME/size against the *declared* metadata at session creation (`KnowledgeServiceImpl`, Testcontainers HTTP test); magic-byte/size-overrun against the *actual* bytes as they're streamed to disk (`LocalFilesystemStorageService`, a **pure JUnit unit test with no Docker/Spring context at all** — `LocalFilesystemStorageServiceTest`, the one part of this ticket fully verifiable in this Gate-H0-constrained dev environment); and a final existence/size/checksum re-check at `complete` time against whatever the storage layer reports back, never trusting the two earlier steps alone.

**What's real but untestable here:** `S3StorageService` is written against the actual AWS SDK v2 API (verified: `S3Presigner` and its model classes are bundled directly in the `software.amazon.awssdk:s3` artifact in the current SDK version — there is no separate `s3-presigner` module, confirmed by inspecting the resolved jar and Maven Central's search API after `services/api/pom.xml`'s first attempt to declare one as a dependency failed to resolve). It is compile-verified only — Gate H3 (no AWS tenant/bucket/credentials) is the same category of environment limitation this project has already recorded for Docker (Gate H0) and Auth0 (Gate H1), not a new kind of gap. Its `metadataOf` deliberately returns a `null` checksum (S3's `ETag` isn't a reliable SHA-256 for multipart uploads, and real checksum verification needs the uploading client to opt into S3's trailing-checksum feature, which this ticket doesn't implement) — `KnowledgeServiceImpl.completeUpload` treats a `null` actual checksum as "size-verified only," never as a checksum match it didn't actually perform.
