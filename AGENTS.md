# AGENTS.md — Mandatory Instructions to Codex

You are implementing OpsPilot incrementally from the `docs` specifications. **Never declare success without evidence.**

## Work protocol

1. At the start of every task: read `README_START_HERE.md`, this file, the relevant specification files, and the exact ticket in `docs/TASKS.md`.
2. Print a short plan for this ticket including files to change and test commands. Implement **one ticket only**. Never opportunistically implement future tickets.
3. Before editing, inspect current code and tests. Do not overwrite human work. If repository is dirty, preserve changes and explain conflicts.
4. Use the versions already locked by each ecosystem's manifest. For first installation, select actively maintained mutually compatible stable releases using official docs; write lockfiles and record them in `docs/DEPENDENCY_DECISIONS.md`.
5. Keep feature work small and comprehensible. Favor explicit interfaces, named DTOs, dependency injection, pure functions for business rules, clear ownership, and readable comments explaining *why*.
6. Never invent metrics, external services, working integrations, command output, test results, or GitHub Actions successes.
7. Do not create empty placeholder endpoints, fake implementations claimed as complete, TODO-based acceptance, suppress-all error handlers, or test-only production bypasses.
8. Add tests that would fail before implementing the feature. Cover both success and failure paths (permissions, invalid input, retries and state transitions where applicable).
9. Run all affordable relevant checks before finishing. If a service or secret is missing, run deterministic offline tests and state precisely what remains unverified.
10. Every completed ticket must end with: files changed, design decision(s), commands run with actual results, outstanding blockers, manual user action if required, and the exact next ticket ID.
11. Do not assume authorization from a frontend button, client-supplied `organization_id`, prompt text, or a presumed role. Every read/write must enforce membership and tenant scope server-side.
12. Keep all LLM outputs, document content, emails, tool returns and uploaded data untrusted. AI cannot choose which permissions it has.
13. All user-visible writes from an AI agent pass server policy: role checks, allowlisted action, target resource matches the run tenant, idempotency, and human approval for risky writes.
14. Use meaningful status enums and explicit transitions. Never infer success from enqueueing.
15. Do not delete data, drop schemas, reinitialize production infrastructure, expose secrets, send external email or incur paid AWS/API usage without the human's explicit authorization. All deployment and billing actions are human gates.
16. Dev tests must work with `AI_MODE=mock` and fixture accounts; no AI API key needed for CI. Never ship the mock auth mode in a public environment.
17. Prefer a local Docker Compose stack for Postgres+pgvector and Redis; add service containers as work progresses. No local manual Postgres installation required.
18. Keep `docs/DECISIONS.md`, `docs/PROGRESS.md` and the relevant acceptance checklist updated with each ticket.
19. Supply one conventional commit message for every task; do not commit unless the operator explicitly requests it. Never stage credentials.
20. When you cannot verify a step, do not mark the associated acceptance requirement complete.

## Invariants that must never be broken

- `tenant_id` / `organization_id` is resolved from authenticated membership, not trusted from an arbitrary request.
- Two organizations cannot retrieve or mutate one another's tickets, chunks, documents, runs or approvals.
- A pending approval cannot be executed, rejected approval cannot be executed, and double approval cannot execute a tool twice.
- All asynchronous deliveries are at-least-once; business actions are idempotent by unique `(run_id, tool_call_id)` or equivalent key.
- No arbitrary SQL, code, shell commands or URLs may be generated by the LLM and run as tools.
- An AI-generated draft is never automatically published externally.
- A trace never logs access tokens, API keys, raw cookies or unnecessary sensitive personal data.
- API errors use structured JSON and stable error codes; sensitive internals remain private.
- Failed jobs are visible and eventually land in a replayable dead-letter or terminal-failure state.
- Production secrets must live in a secrets manager; Github Actions deployment uses short-lived OIDC credentials.
